## 1. 产品定位

### 1.1 一句话

本仓库是一个**本机单用户的垂直领域 RAG 问答应用**：把本地 `corpus/*.txt` 分块、建稠密 + BM25
双索引，在线做双通道召回 → RRF 融合 → 重排 → 上下文预算装配，再交给本地 Ollama 流式生成，
前端是 Streamlit 单页对话（`README.md:3`、`chatbot.py:L3959-L4097`、`chatbot.py:L4904-L4970`）。

当前语料是**毛泽东文集 / 毛泽东选集**（997 篇），所以业务上它是一个"**史料/文献检索问答台**"：
用户用自然语言提问，系统从原文中找相关段落，拼进 prompt，由本地小模型（默认 MiniCPM5-2B）
生成中文回答。它**不是**通用聊天机器人，也**不是**搜索引擎或文献数据库。

### 1.2 谁在用

系统是单机单用户（`README.md:206`），因此"角色"不是权限角色，而是**同一个人在不同时刻戴的帽子**：

| 角色（帽子） | 关心什么 | 主要入口 | 代码/文档证据 |
|---|---|---|---|
| 提问者（终端用户） | 问得对不对、答得快不快、能不能停、答案是否可追溯 | Streamlit 页面（唯一 UI） | `chatbot.py:L4904-L4970` |
| 知识库维护者 | 语料改了要不要重建、重建哪一步、要跑多久 | CLI `process / index / sparse / stages` | `chatbot.py:L5801`、`chatbot.py:L5675-L5678` |
| 词表维护者 | 别名归一是否生效、停用词是否误伤实义词 | `lexicon/` + `python chatbot.py lexicon` | `chatbot.py:L5430-L5471`、`lexicon/aliases.txt:L1-L3` |
| 部署者 | 本机起服务 / 上 ModelScope 容器，模型与数据是否同源 | `start.sh`、`Dockerfile`、`python chatbot.py all` | `start.sh:L247-L266`、`Dockerfile:L1-L9`、`chatbot.py:L4568-L4600` |
| 诊断者 | 一轮为什么慢、为什么答非所问、为什么失败 | `rag.log`、`artifacts/turns.jsonl`、trace steps | `chatbot.py:L4179-L4215`、`chatbot.py:L365-L464` |

**没有**的角色：多租户管理员、审核员、内容运营——登录门是自报手机号识别（无密码、
无短信、无 IdP），能回答"这次是谁在用"，但不构成账号体系或权限模型（`.env` 现在开在
`RAG_LOGIN_ENABLED=1`）。

### 1.3 解决什么问题（以及明确不解决什么）

**解决**：
1. 私有语料不便上传云端，但需要"能对话式检索"——全链路本机：嵌入/重排模型在本地目录
   （`chatbot.py:L1002-L1003`），生成走本地 Ollama（`chatbot.py:L570-L572`），向量库是本地
   Qdrant 进程（`start.sh:L134-L151`）。
2. 小模型（2B 级）+ 8G 内存规格下，也要有"像样的检索质量"——用双通道召回 + 重排补模型能力，
   而不是堆大模型（`chatbot.py:L3959-L4097`；参数默认值见 `chatbot.py:L847-L858`）。
3. 数据可维护：改语料、换模型、换词表分别有独立命令与**指纹闸门**，避免"改了没生效还以为生效"
   （`chatbot.py:L5659-L5678`、`chatbot.py:L3823-L3921`）。

**不解决**（`README.md:204-209` 明确列出）：
- 多用户、并发队列、鉴权（登录门存在但是可选装饰，见 §3.4）；
- 非 `*.txt` 语料（无 PDF/Word/网页抓取，`chatbot.py:L828`）；
- 引用回指点选、答案审校、拒答策略（生成侧不重试、不拒答、无长度闸，`chatbot.py:L608-L609`）；
- 会话持久化（历史只在 Streamlit `session_state`，刷新即丢，`chatbot.py:L4960-L4961`）；
- HTTP API（本版本没有 API 进程；代码中提到 "/ask" 与"API 侧"是历史/预留注释，
  `chatbot.py:L4083`、`chatbot.py:L4792`、`chatbot.py:L4825`）。

## 3. 业务规则与取舍

这一节是本文的核心：**每条规则背后都有一个被放弃的选项**。理解取舍比记住规则重要。

### 3.1 回答口径：不发 system、资料走 user、靠标签划边界

| 规则 | 实现 | 放弃的选项 | 业务后果 |
|---|---|---|---|
| 不发 system prompt（恒空字符串） | `chatbot.py:L3140-L3142`、`chatbot.py:L3526` | 用 system 写"你是毛泽东研究助手，请仅依据资料回答" | 回答风格/人设不可配；模型可能用自身先验回答，**答案不保证仅出自语料** |
| 检索资料恒以 **user 角色**随本轮提问发出 | `chatbot.py:L3140-L3142`、`chatbot.py:L3491-L3499` | 把资料放 system（更"像指令"、模型更服从） | 资料与提问同权，资料正文里的祈使句可能被当指令——用标签兜（下一行） |
| 每条资料包一层结构化 `<document ...>` | `chatbot.py:L3034-L3039`、`chatbot.py:L3044-L3068` | 纯拼接（最"裸"，最省 token） | 标签是"这是数据不是指令"的唯一防线；关掉（`RAG_CONTEXT_TAGS=0`/`META=0`）就回到纯拼接 |
| 当前 `.env`：`RAG_CONTEXT_META=1`、`LABELS=0`、`TAGS=0` | `.env` 生效值；优先级见 `chatbot.py:L3106-L3114` | — | META 模式**接管**包裹：资料仍是带 `index/source/id/chunk/score` 的 `<document>`，只是没有 `[n]（来源：…）` 标头（`chatbot.py:L3044-L3047`） |
| 温度 0（贪心）、presence_penalty 归零 | `chatbot.py:L585-L586`、`chatbot.py:L600-L605` | 用模型自带 presence_penalty=1.5 | 问答稳定可复现；避免惩罚压制人名/术语的正常复现（业务上很重要：史料问答里人名高频） |
| think 默认关；开启时与正文共预算、不进上下文 | `chatbot.py:L573-L574`、`chatbot.py:L4767-L4776` | 用思维链提升推理质量 | 2B 模型上思维链可能吃光输出预算导致"正常结束但 0 字正文"，页面会显式提示关掉 `RAG_THINK`（`chatbot.py:L4766-L4776`） |

**关键业务结论**：系统**没有"回答必须引用资料"的硬约束**。它提供的是"资料进得更靠前、更容易被
模型用上"，是否引用、引用几条，取决于模型自己。可追溯性目前是**半成品**：prompt 里有编号，
但 UI 不渲染资料清单（`chatbot.py:L4825`），`confidence_signal` 也只统计、不判定、不拒答
（`chatbot.py:L2983-L2984`）。这是选择"不做拒答/不做审核"的直接代价。

### 3.2 失败语义：宁可显式红，不可静默错

| 场景 | 规则 | 实现 | 业务理由 |
|---|---|---|---|
| 空查询/纯标点 | 不再守卫，直接透传检索（空结果 → 仍照常生成） | `chatbot.py:L4282-L4284`（守卫 2026-10-29 移除，遗留注释） | 不崩、不吞、零特判；稀疏侧哨兵/降级兜底，不新增分支 |
| 检索为空 | **不拒答**，走纯对话 | `chatbot.py:L4149-L4156` 明确"检索为空也照常生成" | 宁可有答案不可答非所问；风险交给人看（与 3.1 结论一致） |
| 生成失败/空答/未正常结束 | **不入历史**，并回滚本轮的孤儿提问 | `chatbot.py:L4788-L4793`、`chatbot.py:L4854-L4868`、`chatbot.py:L4800-L4806` | 否则下一轮会把没有配对的提问当历史重发，出现"同题被答两遍"（`chatbot.py:L4801-L4803`） |
| 生成被 `num_predict` 截断 | 显式 warning（`done_reason=length`） | `chatbot.py:L4777-L4784` | 答案没写完必须让用户知道，不能看起来正常 |
| 生成流中途错误 | 当场写日志 + 页面 `st.error` + 处置建议 | `chatbot.py:L4750-L4752`、`chatbot.py:L4761-L4765` | 错误元素与残缺正文**并存**，不互相覆盖（`chatbot.py:L4757-L4759`） |
| 无进展（上游僵死） | 读空闲超时 + 整轮硬上限，把"卡死"变"显式错误" | `chatbot.py:L580-L584` | 不是限制正常长答案，只兜无进展 |
| 生成失败分类提示 | 表驱动：404 / OOM / 500 / 连接 | `chatbot.py:L4687-L4728` | 加一类错误只加一行数据；顺序即优先级（`L4718-L4722` 记了旧顺序的误报事故） |
| Stop 中断 | 主动 `close()` 上游流，再回滚、再上抛 | `chatbot.py:L4808-L4819`、`chatbot.py:L4845-L4853` | 单槽 Ollama：断开的生成若继续烧 `num_predict`，后续请求全排队（`chatbot.py:L4809-L4814`） |

### 3.3 一致性与质量闸门：fail-closed

四条**业务级**不变量，都是"对不上就不许检索"，而不是"尽量服务"：

| 闸门 | 校验什么 | 失败表现 | 实现 |
|---|---|---|---|
| 分块指纹闸门 | 索引里记的分块指纹 vs 当前"切分配置 + 每份源文本 sha" | 抛错，提示 `process && index` | `chatbot.py:L3823-L3853`、`chatbot.py:L1540-L1556` |
| 词表指纹闸门 | 索引里记的词表指纹 vs 当前词表（别名/停用词/BM25 编码） | 抛错，提示 `sparse` | `chatbot.py:L3854-L3888` |
| 混合态闸门 | 集合内是否同时存在多个词表指纹（sparse 中断残留） | 抛错，提示 `sparse` | `chatbot.py:L3889-L3921`、`chatbot.py:L2053-L2060` |
| 词面归属冲突闸门 | 别名表**可唯一解析**：同一词面不得同时归属多个规范名（解析处即判，分类与校验器共用 `_alias_owner_conflicts`） | 运行时加载即 RuntimeError（fail-closed），查询/入库/重建/评估所有入口同拦；文件缺失/编码坏仍按"资源类"显式降级为空词表 | `chatbot.py:_read_aliases`、`chatbot.py:_alias_owner_conflicts` |

取舍：**可用性让位于正确性**。用户可能遇到"页面直接报错要求重跑命令"，而不是"安静地给旧知识库
的答案"。这是有意的（`README.md:53`）。代价是：语料一改、人没跑重建，服务就从"能用"变成"不能用"。

### 3.4 交互约束：极简 UI 是产品决策，不是未完成

`run_streamlit()` 里只有：宽屏、登录门（可选）、空库提示、消息列表、一个输入框
（`chatbot.py:L4904-L4970`）。**没有** `top_k` 滑块、来源过滤、温度、模型切换、资料清单展示。
`top_k` 固定为代码默认（调用处 `chatbot.py:L4823` 传入 `TOP_K`，默认 5，`chatbot.py:L847`）。

取舍：把调参权收回到"改 `.env` + 重启"这一条路径（`README.md:78`：代码默认值为唯一权威，
`.env` 只做覆盖层）。业务好处是"任何一次回答都可归因到确定的配置"，坏处是普通用户无法自己
把"答得太泛"调成"更聚焦"。

登录门额外有一个平台约束：ModelScope 创空间只能 iframe 内登录，Safari/禁第三方 Cookie 会失败，
所以代码把 Cookie 名打进日志用于定位（`chatbot.py:L4883-L4901`）——这是"业务上要登录、
平台又限制登录方式"的折中，且用开关（`RAG_LOGIN_ENABLED`）而不是删配置来保留仓库侧的
决定权（`chatbot.py:L4876-L4880`）。

## 4. 数据资产业务口径

> 统计命令只读文件，未触发任何重建。体积同时给"逻辑大小"与"占盘大小"（JSON/mmap 差异大时两者都要）。

### 4.1 corpus（知识源头）

| 指标 | 数值 | 说明 |
|---|---|---|
| 文件数 | **997** 个 `*.txt` | 全部为 `corpus/*.txt`（`chatbot.py:L828` 的 `RAG_DOC_GLOB`） |
| 总字节 | **7,822,764 B（约 7.5 MiB）** | `du` 显示 9.6M（含文件系统块开销） |
| 总字符 | **2,652,052** 字符 | UTF-8 中文为主，约 1 字 ≈ 2.95 字节 |
| 总行数 | **36,691** 行（`wc -l`；若按"每文件末行亦计"则为 37,688） | 文本型语料，无表格/图片 |
| 单文件均值 / 中位 | **7,846 B / 2,923 B** | 典型是"一篇讲话/电报"的体量 |
| 分位数 | p90 ≈ 17 KB、p99 ≈ 72.6 KB | 长尾明显 |
| 最大 / 最小 | **210,595 B**（`毛泽东文集 第1卷 018 寻乌调查.txt`）/ 336 B | 最大单篇是调查报告，属于"一本书里的一章" |
| 体积分布 | <10 KB 共 **794** 篇（79.6%）；≥100 KB 仅 **4** 篇 | 验证了"分块必须按文档自适应"的设计动机 |

业务含义：
- 997 个"文档"其实对应**8 卷文集 + 5 卷选集**里的单篇，文件名即来源标签
  （`source` 字段，`chatbot.py:L829`、`chatbot.py:L1029-L1032`）。所以"来源"粒度是**篇名**，
  不是书名——回答里回指到"第几卷 第几篇"是可做到的（文件名自带卷号与序号）。
- 篇幅差距 600 倍以上：分块参数必须是**token 上限**而非固定字符数（`chatbot.py:L953-L969`）。

### 4.2 分块产物（`artifacts/`）

| 产物 | 内容 | 业务含义 | 证据 |
|---|---|---|---|
| `artifacts/chunks.json`（**63,962,821 B ≈ 61 MiB**） | 全部子块平铺数组，**21,255** 条 | 检索的最小"命中单元"；一条含 `child_text/parent_text/contextual_text/id/source/chunk_index/total_chunks/parent_id/parent_chunk_count` | `chatbot.py:L1011`、`chatbot.py:L1024` |
| `artifacts/chunks.meta.json`（98 KB） | 指纹 + 逐文档 sha + 配置快照 + 计数 | 四阶段体检与"哪些文档可复用"的唯一依据 | `chatbot.py:L1014-L1015`、`chatbot.py:L1772-L1779` |
| `artifacts/docs/`（**997** 个 JSON） | 单文档分块缓存，最大 1.69 MB（寻乌调查） | 改一篇只重算一篇，process 从"全量"变"增量" | `chatbot.py:L1018`、`chatbot.py:L1609-L1652` |

当前 meta 关键值：`fingerprint=923236fe7e4acc7c`、`total_chunks=21255`、`total_parents=4852`、
`reused_documents=0`、`build_time=2026-10-23T20:15:50`。切分配置快照（决定了指纹，改动即全量重建）：

```text

text_opencc=t2s       normalize_quotes=true   splitter=0.33.0
embed_model=./models/bge-m3  embed_model_content=23d8f4c1c39f  chunking_code=888afa9b7f3ff2c8
```

业务含义（父块/子块双层）：
- **子块 21,255 条**用于"精确命中"（128 token 上限，适合嵌入与重排）；
- **父块 4,852 条**用于"给模型看的上下文"（512 token 上限）；
- 检索按子块命中、按 `parent_id` 折叠去重后，把**父块正文**送进 prompt

- 平均每父块约 4.4 个子块（21255 / 4852），与 512/128 的比例大致吻合。

## 5. 业务主流程

### 5.1 首次建库（从零到可问答）

| 步 | 动作 | 命令/入口 | 成功判据 | 失败兜底 |
|---|---|---|---|---|
| 1 | 起服务 | `./start.sh start`（本机）或容器入口 | Qdrant `/healthz`、Ollama `/api/version`、应用 `/_stcore/health` 都就绪 | 拒绝复用"本脚本之外的实例"，防假发布（`start.sh:L62-L77`、`start.sh:L140/L159/L175`） |
| 2 | 分块 | `./start.sh process` | 生成 `chunks.json` + meta 指纹；单篇失败只跳过自己，有失败则**不覆盖**旧产物 | 逐文档兜底，末尾短路（`chatbot.py:L1791-L1793`） |
| 3 | 建索引 | `./start.sh index` | 集合点数 = 产物条数；切片后原子切别名 | 单写者锁 fail-fast、陈旧锁自动接管（`chatbot.py:L4223-L4231`、`chatbot.py:L4300-L4341`） |
| 4 | 体检 | `./start.sh stages` | 四段全绿、退出码 0 | 退出码 1 + 最小重跑命令（`chatbot.py:L5659-L5664`、`chatbot.py:L5795-L5797`） |
| 5 | 打开页面 | `http://127.0.0.1:8501` | 首问能流式出字 | 预热失败只告警，首问冷加载（`chatbot.py:L5030-L5031`） |

业务约束：单写者。`index` 与 `sparse` 共用一把锁，因为并发重建会写坏同一份缓存、或把稀疏向量写到
被删集合上（`chatbot.py:L4223-L4231`）。所以"两个人同时重建"在业务上是不允许的——这与单机单用户
定位一致。

### 5.2 日常问答（一次提问的完整业务时序）

1. 用户输入 → 写入会话（`chatbot.py:L4966`）。
2. 检索：**指纹闸门**（分块 + 词表，仅首次通过后置位）→ 稠密/稀疏并发召回（payload
   全字段随召回返回）→ 加权 RRF → 父块去重 → **全体候选重排（不截断）** → top_k
   （`chatbot.py`）。
   - 降级点都会写 `_degraded` 说明（例如稀疏通道失败仍可用稠密，`chatbot.py:L4000-L4007`、
     `chatbot.py:L2927-L2931`）；业务上"部分降级"必须可见，不能冒充正常。
3. 装配：`<document>` 块按检索顺序拼接 → token 预算（输入上界 = 动态派生窗口 − `RAG_INPUT_RESERVE`；窗口 = min(模型原生, 内存档位)）
   → 历史从旧到新整轮淘汰（`chatbot.py:L3525-L3562`、`chatbot.py:L3380-L3404`）。
4. 生成：单事件契约，首事件恒为 `retrieval`，之后 `thinking/delta/error/done`
   （`chatbot.py:L4153-L4178`）；UI 边收边渲染（`chatbot.py:L4731-L4785`）。
5. 收尾：成功才入历史；失败回滚孤儿提问；台账落盘（`chatbot.py:L4854-L4868`、`chatbot.py:L4179-L4215`）。

### 5.3 数据维护（"该跑哪个命令"的业务判断）

四阶段体检把"改了什么"映射成"最小重跑"（`chatbot.py:L5675-L5678`）：

| 阶段 | 含义 | 什么改动会让它过期 | 最小重跑 | 判断依据 |
|---|---|---|---|---|
| **A 分块** | `chunks.json` + 指纹 | 改语料、改切分参数、改切分代码 | `process && index` | 配置指纹 + 每篇 sha（`chatbot.py:L1896-L1922`） |
| **B 稠密** | 嵌入缓存是否完整覆盖当前产物 | 换嵌入模型、新增内容 | `index`（走缓存增量） | 缓存键覆盖检查（`chatbot.py:L5711-L5741`） |
| **C 稀疏** | 词表/BM25 编码是否与索引一致 | 改别名/停用词/BM25 选项 | `sparse` | 词表指纹全量滚动（`chatbot.py:L5743-L5779`） |
| **D 入库** | 集合是否存在、点数是否等于产物条数 | 集合缺失/重建中断 | `index` | 点数对比（`chatbot.py:L5780-L5788`） |

业务规则：**"未验证"与"已过期"同权**（都让退出码变 1），因为自动化只能用退出码判断要不要重跑
（`chatbot.py:L5737-L5741`、`chatbot.py:L5793-L5797`）。改代码/改 `.env` 不生效时的标准动作是
`stop && start`，因为 `start.sh` 会复用已在跑的进程（`README.md:200`、`start.sh:L169-L183`）。

## 7. 风险、边界与已知降级

### 7.1 业务上不支持 / 会碰壁的场景

| 场景 | 结果 | 依据 | 缓解 |
|---|---|---|---|
| 多人同时用 | 串行排队（单槽生成），长回答会阻塞后续提问 | `.env OLLAMA_NUM_PARALLEL=1`、`chatbot.py:L4809-L4814` | 单机单用户定位，不做 |
| PDF/Word/网页语料 | 不读，只认 `*.txt` | `chatbot.py:L828` | 先转 txt |
| 问"今天天气" | 仍会生成（不拒答），答案来自模型先验 | `chatbot.py:L4149-L4156` | 业务上必须人工判断；系统只给 confidence 数据，不判定（`chatbot.py:L2983-L2984`） |

| 想用外部嵌入服务（infinity） | 本版本不内置，查询会报错 | `README.md:201`、`start.sh:L127-L132` | 保持 `RAG_EMBED_BACKEND=torch`，或自建服务 |

### 7.2 已知降级（会用，但必须显式告警）

| 降级点 | 表现 | 兜底行为 | 证据 |
|---|---|---|---|
| 稀疏召回失败 | 只剩稠密通道 | 记 `_degraded` 并继续（`tolerate_sparse_error`） | `chatbot.py:L4000-L4007`、`chatbot.py:L2927-L2931` |

| 单轮台账写失败 | 不影响本轮 | 只告警 | `chatbot.py:L1044-L1058` |

### 7.3 观察到的文档/文案不一致（低风险，建议后续修）

- `_qdrant_gate` 的失败提示仍写"请先确认服务已启动: docker compose up -d"
  （`chatbot.py:L4435`），但本仓库明确**不使用 compose**（`README.md:5`、`Dockerfile:L1`），
  而实际本机启动方式是 `./start.sh start`（`start.sh:L1-L22`）。人照着提示做会找不到文件。
- 窗口配置变迁：2026-10-28 曾把 `RAG_NUM_CTX` 从 131072 下调到 32768（8G 防 OOM）；2026-10-31 直接**删除该配置**，改为运行期从 Ollama `/api/show` 动态读模型原生窗口（MiniCPM5-2B=131072）：窗口是模型属性，同一份代码/`.env` 在本地与容器都自动用满当前模型的真实能力。
  8G 档换页是显式接受的代价；持续换页只能升级内存或换更小窗口的模型（没有"把窗口调小"的配置了），并盯 `[mem]` 熔断日志。

## 8. 验收与观测口径（运维可按此判断"能不能用"）

| 检查项 | 期望 | 命令/位置 | 失败含义 |

## 9. 关键结论（给后续维护者的 10 条）

1. **定位**：单机单用户的垂直领域 RAG 问答台，语料是毛泽东文集/选集 997 篇（7.8 MB / 265 万字符），
   目标是在 2B 模型 + 8G 档下拿到"可用的检索质量"（`README.md:3`、`chatbot.py:L824-L830`）。
2. **回答口径是"最小 prompt"**：不发 system、资料走 user、只留结构化 `<document>` 标签
   （`chatbot.py:L3140-L3142`、`chatbot.py:L3034-L3068`）。因此**没有"必须依据资料"的硬保证**，
   可追溯性目前只到 prompt 编号，UI 不展示（`chatbot.py:L4825`）。
3. **失败必须显式**：不重试、不拒答、无长度闸；空答/截断/报错都进 UI 与日志
   （`chatbot.py:L4731-L4785`、`chatbot.py:L608-L609`）。代价是"用户会看到错误"，收益是"不会安静地错"。
4. **可用性让位于正确性**：分块/词表/混合态三道 fail-closed 闸门
   （`chatbot.py:L3823-L3921`）。改了语料不重跑，服务就是不可用而不是旧库。
5. **数据资产重心不在语料**：语料 7.5 MB，资产总量约 7.5 GB（模型 6.9 G、索引+缓存 0.8 G）。
   部署与备份要按"GB 级"对待（`Dockerfile:L31-L63`）。
6. **分层检索是质量的核心机制**：21,255 子块负责精准命中、4,852 父块负责给模型完整上下文，
   中间用父块去重控制 token（`chatbot.py:L2971-L2982`、`chatbot.py:L4039-L4046`）。
7. **运维只有 4 个动作**：改语料→`process+index`、换模型→`index`、改词表→`sparse`、
   不确定→`stages`（`chatbot.py:L5659-L5678`）。且重建是**单写者**，并发直接被拒
   （`chatbot.py:L4300-L4341`）。
8. **UI 极简是决策**：没有参数面板、没有来源面板、没有会话持久化
   （`chatbot.py:L4904-L4970`）。所有可调项都在 `.env`，配置唯一权威是代码默认值（`README.md:78`）。
9. **同源优先于性能**：本地与容器共用同一份 `.env`/`artifacts`/`storage`，模型按同文件清单下载
   （`Dockerfile:L31-L51`、`README.md:182-185`）；性能差异来自硬件（MPS vs 2vCPU），不是代码分叉。
10. **最大的两个落地风险**：① ~~8G 档沿用 `.env` 的 `RAG_NUM_CTX=131072` 会 OOM~~（2026-10-31 起窗口动态用满模型原生值 131072，8G 换页为已接受代价；无配置可回退，只能升级内存/换小窗口模型）；
    ② 错误提示里仍有 `docker compose` 的旧文案（`chatbot.py:L4435`），与实际启动方式不一致。
