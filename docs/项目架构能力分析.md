## 0. 执行摘要

### 0.1 项目本质

这不是一个“RAG Demo”，而是一台**为 2vCPU/8G 单容器平台打磨过的单租户 RAG 知识问答 appliance（一体机）**：

- **业务形态**：单文件 Python 应用 `chatbot.py`（5,460 行、210 个函数、5 个类）同时承担 CLI 与 Streamlit 前端；离线用 4 条命令生产知识库，在线提供“双通道召回 → RRF 融合 → 父块去重 → 重排 → 预算装配 → 流式生成”。
- **技术底座**：Streamlit 1.62 + Qdrant 1.19（稠密 bge-m3 1024 维 + 服务端 BM25 稀疏）+ Ollama 0.34（MiniCPM5-2B Q4_K_M）+ bge-reranker-v2-m3；嵌入/重排默认进程内 torch（MPS/CUDA/CPU），也可切 HTTP（infinity）。
- **交付形态**：同一套配置与模型清单，派生三种部署——魔搭创空间**单容器三进程**、自有服务器 **compose 四容器**、macOS **本地原生四件套**。
- **数据规模**：997 篇语料（9.6 MB）→ 21,255 个子块 / 4,852 个父块（`chunks.json` 61 MB）→ Qdrant 集合 21,255 点（storage 230 MB）；本地模型 6.9 GB（仅 2 个现役）。

### 0.2 核心判断

这个项目最突出的能力不是检索算法本身，而是**把“知识库正确性”工程化成了可执行、可失败、可追溯的状态机**：

1. **可验证的知识生产**：四阶段 `process → index → sparse → stages`，三类指纹（切分 / 词表 / 稠密缓存三元组）+ 四道 fail-closed 闸门 + “新集合 + 原子切别名”，让“产物是否过期”不靠人记。
2. **可解释的混合检索**：双通道并发召回、客户端加权 RRF、按 id 精确回取、父块去重、全候选统一重排，每一层都有降级记录与 steps 证据。
3. **可预算的生成装配**：全链路只用一个 token 度量；历史整轮淘汰、资料整条让位、锚点 token 截取；整条 prompt 估算 ≤ 输入上界由 `RuntimeError` 守住。
4. **可自愈的单容器交付**：entrypoint 进程级巡检 + 指数退避就地重启 + OOM 观测，把 8G 容量矛盾转化为“短暂不可用后恢复”，而不是整容器失败。
5. **单一来源的工程纪律**：.env 解析、硬件派生、模型清单、Qdrant 版本、配置审计各自只有一处实现，并靠构建期断言、发布前审计、启动日志三层防漂移。

**一句话评价**：作为“单租户、单机、垂直领域 RAG 生产系统”，架构成熟度约 **4/5**；作为“可复制的多用户知识库平台”，约 **2/5**——差距主要不在检索，而在模块边界、测试/CI、多租户与容量设计。

### 2.2 逻辑分层

| 层 | 组件 | 能力 | 典型依赖 |
|---|---|---|---|
| L0 基座 | 配置解析、日志、硬件探测、运行态单例、Ollama 客户端、模型加载 | 启动即校验、双写日志、并发度派生、设备/精度选择 | 仅标准库 + dotenv；torch/transformers 惰性导入 |
| L1 离线知识生产 | 归一化、父子分块、文档缓存、嵌入缓存、索引构建、sparse 重建、stages | 可增量、可验证、可原子切换 | semantic-text-splitter、torch、Qdrant |
| L2 在线检索生成 | RAGEngine、双通道召回、RRF、去重、重排、上下文装配、事件流 | 可解释、有预算、有降级记录 | Qdrant、torch、Ollama |
| L3 交互 | Streamlit 页面、登录门、Stop、错误提示、历史 | 极简单用户；失败不入历史 | Streamlit |
| L4 运行时 | entrypoint 进程树、健康巡检、自愈、OAuth secrets 装配 | 单容器自愈；重启不重新部署 | bash、curl |
| L5 质量与评估 | deploy-check、config-audit、boot_selftest、eval_retrieval、rerank_parity、quant_*、hw_profile、turn_stats | 发布闸门、基线对拍、量化决策、硬件适配 | 独立脚本 |

**架构风格**：模块化单体（Modular Monolith）的“单文件变体”——逻辑分层清晰、依赖方向单一（上层调下层），但物理边界为零；部署为“单容器多进程 + 外部状态服务（Qdrant/Ollama）”。

### 2.3 离线知识生产数据流

~~~mermaid
flowchart TD
    C[corpus/*.txt<br/>997 篇] --> P[process<br/>归一化 + 父子分块]
    P --> A[artifacts/chunks.json<br/>+ meta + docs/]
    A --> I[index<br/>内容哈希增量嵌入]
    I --> EC[artifacts/embeddings<br/>*.npz]
    I --> Q[(新集合<br/>原子切别名 rag_current)]
    LX[lexicon 词表] --> S[sparse<br/>原地重建稀疏向量]
    S --> Q
    A --> G[stages 四阶段比对]
    EC --> G
    Q --> G
    G -->|全新鲜 exit 0| OK[可服务]
    G -->|有陈旧 exit 1| FIX[最小重跑命令]
~~~

产物由**指纹**绑定：

- 切分指纹 = 切分配置 + 源文本 sha + 分块代码 + 模型内容指纹 + splitter 版本 → 写入 `chunks.meta.json` 与每个点的 `chunk_fingerprint`。
- 词表指纹 = 别名文件内容 + 路径 + 开关 + BM25 选项 + Qdrant 服务端版本 + 6 个函数源码 → 写入每个点的 `lexicon_id`。
- 稠密缓存键 = 模型路径哈希 + 模型内容指纹 + 嵌入代码指纹 + 精度 → 文件名即身份，键为块文本 sha256。

## 3. 架构能力全景

### 3.1 能力矩阵

图例：● 完整闭环；◐ 有实现但有边界/风险；○ 弱或缺失。

| # | 能力域 | 子能力 | 实现要点 | 成熟度 |
|---|---|---|---|---|
| 1 | 知识接入 | 文本读取、编码校验、ftfy/OpenCC、引号归一、别名归一 | 严格 UTF-8 + 精确报错；组件化归一 | ● |

### 3.2 分域说明

**A. 知识生产（能力 1–5）**  
`process` 是唯一的分块入口：逐字读取 → 归一化（ftfy + OpenCC + 引号）→ 父块语义切分 → 子块重叠切分 → 短父块合并 → 逐文档缓存 → 聚合写 `chunks.json`；任一文档失败**不覆盖旧产物**。`index` 先校验产物新鲜度与可开内存，再按块文本哈希复用嵌入，双写 dense+sparse 到新集合，校验点数=产物数后原子切别名。`sparse` 在换词表时只重建稀疏向量与 `lexicon_id`。`stages` 四段 A/B/C/D 比对并给出最小重跑命令，退出码供自动化使用。  
**能力边界**：只支持 `*.txt`；逐文档缓存的全局指纹使“改一篇=全部重切”（真实增量只发生在重跑/失败恢复）；旧 `.npz` 缓存无 GC。

**B. 检索（能力 6–9）**  
`hybrid_search` 先做空查询守卫与指纹闸门，再并发执行稠密/稀疏查询（稀疏请求持全局推理锁，规避 qdrant-client ModelEmbedder 的无锁竞争），客户端按 `weight/(k+rank)` 做加权 RRF，按命中 id 精确回取 payload（避免别名切换取错集合），按 `parent_id` 去重后对**全体候选**统一重排。候选池默认恒等于 `RAG_RERANK_TOP_K`，只有显式预算才收缩并点名，杜绝静默降精度。  
**能力边界**：无相关性阈值/拒答；无查询改写/扩展/缓存；稀疏异常、回取缺失、去重不足等降级只在日志可见（Streamlit 不消费 steps）。

**C. 生成与交互（能力 10–12）**  
资料以结构化 `<document index/source/id/chunk/score>` 块注入，system 恒空、资料恒为 user 角色；输入上界 `I = num_ctx - reserve`，历史按整轮 FIFO 淘汰，资料按整条从尾部让位，最后才 token 级截断锚点，并以 `RuntimeError` 守护硬上界。生成事件词表封闭且首事件必须 `retrieval`；error 与 done 互斥，失败/空答不入历史并回滚孤儿 user；Stop 通过主动关闭生成器链让 Ollama 感知断连。  
**能力边界**：不重试、不拒答、无输出长度闸（显式设计）；Streamlit 不展示来源清单；登录门只控制“能否进页面”。

**D. 工程与交付（能力 13–17）**  
配置层把“非法/矛盾/保留字冲突”全部前移到 import 期；日志解决多进程轮转与 stale-fd；硬件探测派生离线并发/嵌入批/Qdrant 写批；部署层用“单一来源 + 构建期断言 + 配置审计 + 发布闸门”防漂移；运行时用进程级巡检替代应用层内存编排。  
**能力边界**：全部质量手段是本地脚本，没有 CI；单文件使模块级测试难以导入；指纹区禁改与静态检查目标冲突。

**E. 安全与扩展（能力 18–19）**  
当前是“可信环境单租户”假设：端口绑定回环（compose）、单容器由平台网关暴露、当前部署登录门关闭（代码默认开启，.env 置 0）、资料正文未转义、容器 root + 0777 可写目录。没有租户 filter、限流、审计留存、多用户会话持久化。  
**能力边界**：这些不是实现瑕疵，而是产品定位（appliance）决定的；但一旦面向公网多用户，需要整组版本迁移（README B 档）。

## 4. 关键架构机制深潜

### 4.1 指纹-闸门-原子切换：把“产物新鲜度”变成可执行判据

**问题**：RAG 的最隐蔽故障不是报错，而是“服务在正常回答，但用的是旧知识库”。

**机制**：
1. 三类身份：切分指纹（配置+源文本+代码+模型内容）、词表指纹（词表内容+BM25 选项+服务端版本+源码）、稠密缓存键（模型内容+代码+精度）。
2. 三道写入：`chunks.meta.json`、每个点的 payload、缓存文件名。
3. 四道校验：`verify_chunks_freshness`（离线）、`build_index` 键集/维度/点数、在线 `_check_chunk_freshness` / `_check_lexicon_consistency`、`stages` 退出码。
4. 原子切换：新集合写完并通过点数/维度校验后才切别名；失败不切、旧集合继续服务；切别名失败会尝试恢复旧别名并按实际读回结果报错。

**为什么有效**：判据与实现同源（同一函数算“写入指纹”和“当前指纹”），失败一律 fail-closed，且“通过才置位”避免一次网络抖动让整个进程生命周期不再校验。  
**代价**：任何改动指纹单元的代码（含注释/格式）都可能触发全量重建；切分/词表代码被划为“禁改区”，静态检查规则也因此妥协。

### 4.2 双通道并发 + 客户端加权 RRF + 全候选重排

**流程**：空查询守卫 → 指纹闸门 → 稠密查询向量（权重非 0 才计算）→ 稀疏 Document（服务端分词；无内容不发）→ 两路并发 recall（各 `RECALL_LIMIT` 条）→ 客户端 `weighted_rrf` 融合（k=60，零权重通道跳过）→ 按 id 精确回取 payload → 父块去重 → 候选池截断 → 重排（对全部候选打分）→ 输出 top_k。

**设计权衡**：
- 融合放客户端：权重可解释、每路名次可进 steps、可单测；代价是多一次结果回传与客户端排序。
- 稀疏请求持全局锁：规避 qdrant-client 本地推理器无锁导致的串文本/IndexError；代价是稀疏召回串行（双路仍并发，墙钟≈max）。
- 重排 HTTP 契约更严：必须一次返回全部候选分数，少一条直接报错，保护“统一打分”不变量。
- 候选池不自动收缩：本地与容器质量一致；延迟换精度必须用户显式决定。

### 4.3 单一 token 度量与硬上界装配

所有预算/裁剪只调用 `estimate_tokens`：优先生成模型官方 tokenizer（含来源一致性校验），其次 GGUF + llama.cpp 分词，最后保守估算。装配顺序是“先保提问、再保 system、再保资料、最后砍历史”：历史整轮淘汰（不截半句），资料整条从尾部丢（保证 sources 与实际看到的一致），单条仍超才 token 级截前缀，最后才截提问且绝不删空。最终 `message_tokens(out) ≤ input_cap` 用 `RuntimeError` 校验（而非 assert，防 `-O`）。  
**能力边界**：只统计 content，不计 chat template/role/BOS 等特殊 token；当前 `RAG_INPUT_RESERVE=0` 会把这部分风险交给 Ollama 服务端上下文移位（静默丢前文），见 §7。

### 4.4 封闭事件契约与“失败不入历史”

事件只有 5 种：`retrieval / thinking / delta / error / done`。生产端保证首事件恒为 `retrieval`；消费端用 `first_retrieval` 显式断言，`drain_events` 对词表外 kind 直接抛错。`stream_chat` 收到 error 后 **yield 错误并 return**，不再转发后续 done——否则“残缺答案”会同时满足 done+非空而进入历史。Streamlit 只有在“无 error、有 done、正文非空”三条件成立时才 append assistant，并回滚本轮孤儿 user；Stop 走 `BaseException` 分支，先关闭上游生成器再回滚、原样上抛。  
**价值**：把“流式场景下最难查的静默错误”变成显式契约；代价是契约变更必须同时改生产/消费两端。

### 4.5 单一来源 + 构建期断言 + 配置审计

同一知识只保留一处实现：

| 知识 | 唯一实现 | 复用方 |
|---|---|---|
| .env 解析 | `tools/dotenv.sh` | entrypoint、run_local、run_ollama |
| 硬件派生 | `tools/hw_profile.py`（+ shell 薄封装） | 三入口 + chatbot.py 自探测 |
| 模型清单/下载 | `tools/fetch_models.sh` | 构建期烘焙 + 运行期补下 + 自检 |
| 模型选择键 | `.env` + `tools/bake.env` | Dockerfile 逐键断言 |
| Qdrant 版本 | Dockerfile ARG | compose 镜像 tag / run_qdrant.sh |
| 发布检查 | `tools/deploy-check.sh` | 五步闸门 |

构建期断言把“烘焙 A、运行 B”变成构建失败；`config-audit.py` 把“废弃键/无消费方键/模型键漂移”变成发布失败；启动日志打印 `.env` sha256 与关键生效值，解决“线上到底跑哪一档”的归因问题。  
**能力边界**：审计用子串匹配，注释命中也会被当成消费方；校验强度低于 AST 级提取。

### 4.6 进程级巡检自愈：用“可运维”替代“容量解决”

2026-10-24 定稿：**不做应用层内存编排**（无互斥驻留、无自适应/水位、无请求级 keep_alive）。每个进程按自身策略管理内存；OOM 的现实后果是某进程被杀，由 entrypoint 的就地重启兜底：

- 存活判据排除僵尸（`kill -0` + `stat != Z`），健康检查用 HTTP；
- 连续失败/退出 → `kill -9` → 指数退避 `min(120s, 5·2^(n-1))·(1+jitter)` 后重启；
- 重启层级：单进程 → 容器内拉起；PID 1/容器退出 → 平台重拉容器（仍属“重启运行”，非重新部署）；
- 配对观测：`[mem]` 打 cgroup anon 与 RSS Top4，`[watchdog]` 每分钟汇总，`_kv_report` 转印 KV 精度。

**评价**：这是对“8G 容量矛盾无法在应用层解决”的诚实工程回应；但它把“容量不足”转化为“周期性短暂不可用”，不是消除。当前 `turns.jsonl` 已有 `insufficient_memory` 实证。

### 4.7 三形态部署与权重三级策略

| 形态 | 入口 | 进程编排 | 检索模型位置 | 适用 |
|---|---|---|---|---|
| 单容器（魔搭） | `Dockerfile` + `entrypoint.sh` | entrypoint 起 qdrant/ollama(/infinity)/streamlit 并巡检 | 进程内 torch（或可选 infinity） | 2vCPU/8G 平台 |
| compose | `docker-compose.yml` | Docker 负责重启 + 健康依赖 | 独立 embed 容器（HTTP） | 自有 Linux / GPU |
| 本地原生 | `tools/run_local.sh` | 脚本起停 + pid/端口/命令行三一致复用 | 可选 infinity 或进程内 | macOS Metal/MPS |

权重三级策略（烘焙镜像 > `/mnt/workspace` 持久盘 > `/app` 就地下载）与 no-bake 配套；运行期用 symlink 而不是重写 `RAG_EMBED_MODEL_PATH`，因为后者会进切分指纹导致本地/线上指纹不一致。  
**能力边界**：no-bake 后若无持久盘，每次重启需重下 ~6 GB；compose 的 app 仍以 `BAKE_*=1` 构建并绕开 entrypoint（见 §7）。

### 4.8 评估方法论：阈值先登记、基线可跨重建

- `quant_parity.py` 在测量前登记阈值（嵌入余弦 ≥0.999、P1 ≥0.995、重排 Spearman ≥0.99、top1 ≥0.95、吞吐 ≥1.2×、常驻下降 ≥50%），防止“测完再改判据”。
- `eval_retrieval.py` 以“来源文档命中”为跨重建不变量（point id 会变，来源不会），并以退出码作为闸门。
- `rerank_parity.py` 在拆分 HTTP 重排前先证明两条路径同一排序。
- `turn_stats.py` 用 `prompt_eval_count / prompt_tokens_est` 判断 KV 复用还是整段重算。

这套方法让“改动是否让系统变坏”可回答；不足是全部离线、手工触发，没有进入 CI，也没有端到端“答得好不好”的 golden QA。

## 6. 架构优势

1. **把“静默失败”当作一等敌人**：从配置解析、日志轮转、GPU 回落到检索降级，几乎每条路径都写明“旧写法会怎样静默错”，并用具名报错/断言/状态位消除。这是本项目最稀缺的工程文化。
2. **产物状态机而非文件堆**：四阶段 + 三类指纹 + fail-closed + 原子别名切换，使“重建”是幂等、可回滚、可诊断的操作。
3. **离线/在线判据同源**：写入与校验共用同一函数（切分指纹、缓存选择、词表指纹），从结构上消除“判据与实现分叉”。
4. **检索链路可解释**：双通道名次、RRF 资源、去重折叠、候选截断、重排分数都进入 steps（API 侧）；权重与候选池策略显式化。
5. **生成预算硬约束**：单一 token 度量 + 整轮淘汰 + 资料整条让位 + RuntimeError 兜底，长上下文下不会静默越界。
6. **失败语义清晰**：error/done 互斥、失败不入历史、Stop 主动断流、空库/清空是合法终态。
7. **配置与构建的单一来源**：dotenv/hw_profile/fetch_models/版本号/模型键各自一处，且用构建断言和审计脚本防漂移。
8. **对平台缺陷的工程化适配**：mtime 归一、gh-proxy、多段下载、infinity 影子视图、OAuth secrets 装配、no-bake、进程自愈——每条都对应真实事故。
9. **评估方法论成熟**：阈值测量前登记、跨重建基线、先对拍再拆分、台账默认关闭——不把“基准测量”变成日常负担。
10. **注释即决策记录**：关键取舍都带日期、实测数字与“为什么不是另一种写法”，降低后续变更的认知成本。

| # | 风险 | 机制与影响 | 证据 |
|---|---|---|---|

### 8.3 H3：平台化（8 周以上，需版本迁移）

1. **多用户**：按登录 ID 持久会话；Qdrant 租户 filter；队列 + 背压 + 并发上限；KV≈f(并发, ctx) 预算公式；限流。
2. **多格式**：PDF/DOCX 解析纳入分块指纹；版面/表格策略。
3. **查询能力**：多轮查询改写（A1）、查询级缓存（C3）、相关性阈值/拒答策略（需产品决策）。
4. **交付与运维**：镜像 digest 固定、备份/快照、发布流程自动化、端到端监控。
5. **容量**：HNSW/量化（当前 int8/int8e/onnx_int8 因保真未达标被拒，但 int8e 内存 −75% 是现成抓手）、检索模型独立服务化。

### 8.4 不建议做的事

- 不要在未解决 P0-2 前继续增强“清空/重建”自动化——会把静默清库放大。
- 不要在单容器 8G 档继续加应用层内存编排——2026-10-24 已论证无效，只会移动 OOM 时机。
- 不要为通过 lint 而改动指纹区源码——触发全量重建且违反不变量；应继续用精确豁免 + 人工核对清单。

## 9. 结论

1. **架构定位准确**：项目选择“单文件 + 单容器 + 强运维”的 appliance 路线，与其部署平台（2vCPU/8G、无 compose）和单用户场景高度匹配；把复杂度集中在“知识正确性”和“运行可恢复”，而不是抽象层次，是正确的取舍。
2. **工程化水平显著高于同规模项目**：指纹/闸门/原子切换、单一来源配置、构建期断言、量化与检索评估方法论，构成了真正可复用的“RAG 生产化经验”。
3. **主要风险不在算法，而在容量与边界治理**：131k × 8G、重复定义导致的静默清库、no-bake 无持久盘、token 预算与真实 prompt 的偏差，是当前最该修的四个点；compose 路径的一致性问题，是“第二条部署路径”的典型债务。
4. **平台化能力尚未建立**：单用户、无租户/限流/持久会话、无测试/CI，决定了它现在是“一套可交付的系统”，而不是“一个可复制的平台”。若目标是多用户 SaaS，应按 README B 档做整组版本迁移，而不是局部打补丁。
5. **建议的下一步**：先做 H1 的 6 个动作（其中 `_document_paths` 与容量档位是最高性价比），再启动 H2 的模块化与 golden QA；在容量与正确性稳定前，不建议扩展多格式或多用户。
