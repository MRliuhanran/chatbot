## 0. 执行摘要

### 0.1 项目本质

这不是一个“RAG Demo”，而是一台**为 2vCPU/8G 单容器平台打磨过的单租户 RAG 知识问答 appliance（一体机）**：

- **业务形态**：单文件 Python 应用 `chatbot.py`（5,460 行、210 个函数、5 个类）同时承担 CLI 与 Streamlit 前端；离线用 4 条命令生产知识库，在线提供“双通道召回 → RRF 融合 → 父块去重 → 重排 → 预算装配 → 流式生成”。
- **技术底座**：Streamlit 1.62 + Qdrant 1.19（稠密 bge-m3 1024 维 + 服务端 BM25 稀疏）+ Ollama 0.34（MiniCPM5-2B Q4_K_M）+ bge-reranker-v2-m3；嵌入/重排默认进程内 torch（MPS/CUDA/CPU），也可切 HTTP（infinity）。
- **交付形态**：同一套配置与模型清单，派生三种部署——魔搭创空间**单容器三进程**、自有服务器 **compose 四容器**、macOS **本地原生四件套**。
- **数据规模**：997 篇语料（9.6 MB）→ 21,255 个子块 / 4,852 个父块（`chunks.json` 61 MB）→ Qdrant 集合 21,255 点（storage 230 MB）；本地模型 6.9 GB（仅 2 个现役）。

### 0.2 核心判断

这个项目最突出的能力不是检索算法本身，而是**把“知识库正确性”工程化成了可执行、可失败、可追溯的状态机**：

1. **可验证的知识生产**：四阶段 `process → index → sparse → stages`，三类指纹（切分 / 词表 / 稠密缓存三元组）+ 四道 fail-closed 闸门 + “新集合 + 原子切别名”，让“产物是否过期”不靠人记。
2. **可解释的混合检索**：双通道并发召回、客户端加权 RRF、按 id 精确回取、父块去重、全候选统一重排，每一层都有降级记录与 steps 证据。
3. **可预算的生成装配**：全链路只用一个 token 度量；历史整轮淘汰、资料整条让位、锚点 token 截取；整条 prompt 估算 ≤ 输入上界由 `RuntimeError` 守住。
4. **可自愈的单容器交付**：entrypoint 进程级巡检 + 指数退避就地重启 + OOM 观测，把 8G 容量矛盾转化为“短暂不可用后恢复”，而不是整容器失败。
5. **单一来源的工程纪律**：.env 解析、硬件派生、模型清单、Qdrant 版本、配置审计各自只有一处实现，并靠构建期断言、发布前审计、启动日志三层防漂移。

**一句话评价**：作为“单租户、单机、垂直领域 RAG 生产系统”，架构成熟度约 **4/5**；作为“可复制的多用户知识库平台”，约 **2/5**——差距主要不在检索，而在模块边界、测试/CI、多租户与容量设计。

### 2.2 逻辑分层

| 层 | 组件 | 能力 | 典型依赖 |
|---|---|---|---|
| L0 基座 | 配置解析、日志、硬件探测、运行态单例、Ollama 客户端、模型加载 | 启动即校验、双写日志、并发度派生、设备/精度选择 | 仅标准库 + dotenv；torch/transformers 惰性导入 |
| L1 离线知识生产 | 归一化、父子分块、文档缓存、嵌入缓存、索引构建、sparse 重建、stages | 可增量、可验证、可原子切换 | semantic-text-splitter、torch、Qdrant |
| L2 在线检索生成 | RAGEngine、双通道召回、RRF、去重、重排、上下文装配、事件流 | 可解释、有预算、有降级记录 | Qdrant、torch、Ollama |
| L3 交互 | Streamlit 页面、登录门、Stop、错误提示、历史 | 极简单用户；失败不入历史 | Streamlit |
| L4 运行时 | entrypoint 进程树、健康巡检、自愈、OAuth secrets 装配 | 单容器自愈；重启不重新部署 | bash、curl |
| L5 质量与评估 | deploy-check、config-audit、boot_selftest、eval_retrieval、rerank_parity、quant_*、hw_profile、turn_stats | 发布闸门、基线对拍、量化决策、硬件适配 | 独立脚本 |

**架构风格**：模块化单体（Modular Monolith）的“单文件变体”——逻辑分层清晰、依赖方向单一（上层调下层），但物理边界为零；部署为“单容器多进程 + 外部状态服务（Qdrant/Ollama）”。

### 2.3 离线知识生产数据流

~~~mermaid
flowchart TD
    C[corpus/*.txt<br/>997 篇] --> P[process<br/>归一化 + 父子分块]
    P --> A[artifacts/chunks.json<br/>+ meta + docs/]
    A --> I[index<br/>内容哈希增量嵌入]
    I --> EC[artifacts/embeddings<br/>*.npz]
    I --> Q[(新集合<br/>原子切别名 rag_current)]
    LX[lexicon 词表] --> S[sparse<br/>原地重建稀疏向量]
    S --> Q
    A --> G[stages 四阶段比对]
    EC --> G
    Q --> G
    G -->|全新鲜 exit 0| OK[可服务]
    G -->|有陈旧 exit 1| FIX[最小重跑命令]
~~~

产物由**指纹**绑定：

- 切分指纹 = 切分配置 + 源文本 sha + 分块代码 + 模型内容指纹 + splitter 版本 → 写入 `chunks.meta.json` 与每个点的 `chunk_fingerprint`。
- 词表指纹 = 别名文件内容 + 路径 + 开关 + BM25 选项 + Qdrant 服务端版本 + 6 个函数源码 → 写入每个点的 `lexicon_id`。
- 稠密缓存键 = 模型路径哈希 + 模型内容指纹 + 嵌入代码指纹 + 精度 → 文件名即身份，键为块文本 sha256。

## 3. 架构能力全景

### 3.1 能力矩阵

图例：● 完整闭环；◐ 有实现但有边界/风险；○ 弱或缺失。

| # | 能力域 | 子能力 | 实现要点 | 成熟度 |
|---|---|---|---|---|
| 1 | 知识接入 | 文本读取、编码校验、ftfy/OpenCC、引号归一、别名归一 | 严格 UTF-8 + 精确报错；组件化归一 | ● |

### 3.2 分域说明

**A. 知识生产（能力 1–5）**  
`process` 是唯一的分块入口：逐字读取 → 归一化（ftfy + OpenCC + 引号）→ 父块语义切分 → 子块重叠切分 → 短父块合并 → 逐文档缓存 → 聚合写 `chunks.json`；任一文档失败**不覆盖旧产物**。`index` 先校验产物新鲜度与可开内存，再按块文本哈希复用嵌入，双写 dense+sparse 到新集合，校验点数=产物数后原子切别名。`sparse` 在换词表时只重建稀疏向量与 `lexicon_id`。`stages` 四段 A/B/C/D 比对并给出最小重跑命令，退出码供自动化使用。  
**能力边界**：只支持 `*.txt`；逐文档缓存的全局指纹使“改一篇=全部重切”（真实增量只发生在重跑/失败恢复）；旧 `.npz` 缓存无 GC。

**B. 检索（能力 6–9）**  
`hybrid_search` 先做空查询守卫与指纹闸门，再并发执行稠密/稀疏查询（稀疏请求持全局推理锁，规避 qdrant-client ModelEmbedder 的无锁竞争），客户端按 `weight/(k+rank)` 做加权 RRF，按命中 id 精确回取 payload（避免别名切换取错集合），按 `parent_id` 去重后对**全体候选**统一重排。候选池默认恒等于 `RAG_RERANK_TOP_K`，只有显式预算才收缩并点名，杜绝静默降精度。  
**能力边界**：无相关性阈值/拒答；无查询改写/扩展/缓存；稀疏异常、回取缺失、去重不足等降级只在日志可见（Streamlit 不消费 steps）。

**C. 生成与交互（能力 10–12）**  
资料以结构化 `<document index/source/id/chunk/score>` 块注入，system 恒空、资料恒为 user 角色；输入上界 `I = num_ctx - reserve`，历史按整轮 FIFO 淘汰，资料按整条从尾部让位，最后才 token 级截断锚点，并以 `RuntimeError` 守护硬上界。生成事件词表封闭且首事件必须 `retrieval`；error 与 done 互斥，失败/空答不入历史并回滚孤儿 user；Stop 通过主动关闭生成器链让 Ollama 感知断连。  
**能力边界**：不重试、不拒答、无输出长度闸（显式设计）；Streamlit 不展示来源清单；登录门只控制“能否进页面”。

**D. 工程与交付（能力 13–17）**  
配置层把“非法/矛盾/保留字冲突”全部前移到 import 期；日志解决多进程轮转与 stale-fd；硬件探测派生离线并发/嵌入批/Qdrant 写批；部署层用“单一来源 + 构建期断言 + 配置审计 + 发布闸门”防漂移；运行时用进程级巡检替代应用层内存编排。  
**能力边界**：全部质量手段是本地脚本，没有 CI；单文件使模块级测试难以导入；指纹区禁改与静态检查目标冲突。

**E. 安全与扩展（能力 18–19）**  
当前是“可信环境单租户”假设：端口绑定回环（compose）、单容器由平台网关暴露、当前部署登录门关闭（代码默认开启，.env 置 0）、资料正文未转义、容器 root + 0777 可写目录。没有租户 filter、限流、审计留存、多用户会话持久化。  
**能力边界**：这些不是实现瑕疵，而是产品定位（appliance）决定的；但一旦面向公网多用户，需要整组版本迁移（README B 档）。

## 4. 关键架构机制深潜

### 4.1 指纹-闸门-原子切换：把“产物新鲜度”变成可执行判据

**问题**：RAG 的最隐蔽故障不是报错，而是“服务在正常回答，但用的是旧知识库”。

**机制**：
1. 三类身份：切分指纹（配置+源文本+代码+模型内容）、词表指纹（词表内容+BM25 选项+服务端版本+源码）、稠密缓存键（模型内容+代码+精度）。
2. 三道写入：`chunks.meta.json`、每个点的 payload、缓存文件名。
3. 四道校验：`verify_chunks_freshness`（离线）、`build_index` 键集/维度/点数、在线 `_check_chunk_freshness` / `_check_lexicon_consistency`、`stages` 退出码。
4. 原子切换：新集合写完并通过点数/维度校验后才切别名；失败不切、旧集合继续服务；切别名失败会尝试恢复旧别名并按实际读回结果报错。

**为什么有效**：判据与实现同源（同一函数算“写入指纹”和“当前指纹”），失败一律 fail-closed，且“通过才置位”避免一次网络抖动让整个进程生命周期不再校验。  
**代价**：任何改动指纹单元的代码（含注释/格式）都可能触发全量重建；切分/词表代码被划为“禁改区”，静态检查规则也因此妥协。

### 4.2 双通道并发 + 客户端加权 RRF + 全候选重排

**流程**：空查询守卫 → 指纹闸门 → 稠密查询向量（权重非 0 才计算）→ 稀疏 Document（服务端分词；无内容不发）→ 两路并发 recall（各 `RECALL_LIMIT` 条）→ 客户端 `weighted_rrf` 融合（k=60，零权重通道跳过）→ 按 id 精确回取 payload → 父块去重 → 候选池截断 → 重排（对全部候选打分）→ 输出 top_k。

**设计权衡**：
- 融合放客户端：权重可解释、每路名次可进 steps、可单测；代价是多一次结果回传与客户端排序。
- 稀疏请求持全局锁：规避 qdrant-client 本地推理器无锁导致的串文本/IndexError；代价是稀疏召回串行（双路仍并发，墙钟≈max）。
- 重排 HTTP 契约更严：必须一次返回全部候选分数，少一条直接报错，保护“统一打分”不变量。
- 候选池不自动收缩：本地与容器质量一致；延迟换精度必须用户显式决定。

### 4.3 单一 token 度量与硬上界装配

所有预算/裁剪只调用 `estimate_tokens`：优先生成模型官方 tokenizer（含来源一致性校验），其次 GGUF + llama.cpp 分词，最后保守估算。装配顺序是“先保提问、再保 system、再保资料、最后砍历史”：历史整轮淘汰（不截半句），资料整条从尾部丢（保证 sources 与实际看到的一致），单条仍超才 token 级截前缀，最后才截提问且绝不删空。最终 `message_tokens(out) ≤ input_cap` 用 `RuntimeError` 校验（而非 assert，防 `-O`）。  
**能力边界**：只统计 content，不计 chat template/role/BOS 等特殊 token；当前 `RAG_INPUT_RESERVE=0` 会把这部分风险交给 Ollama 服务端上下文移位（静默丢前文），见 §7。

### 4.4 封闭事件契约与“失败不入历史”

事件只有 5 种：`retrieval / thinking / delta / error / done`。生产端保证首事件恒为 `retrieval`；消费端用 `first_retrieval` 显式断言，`drain_events` 对词表外 kind 直接抛错。`stream_chat` 收到 error 后 **yield 错误并 return**，不再转发后续 done——否则“残缺答案”会同时满足 done+非空而进入历史。Streamlit 只有在“无 error、有 done、正文非空”三条件成立时才 append assistant，并回滚本轮孤儿 user；Stop 走 `BaseException` 分支，先关闭上游生成器再回滚、原样上抛。  
**价值**：把“流式场景下最难查的静默错误”变成显式契约；代价是契约变更必须同时改生产/消费两端。

### 4.5 单一来源 + 构建期断言 + 配置审计

同一知识只保留一处实现：

| 知识 | 唯一实现 | 复用方 |
|---|---|---|
| .env 解析 | `tools/dotenv.sh` | entrypoint、run_local、run_ollama |
| 硬件派生 | `tools/hw_profile.py`（+ shell 薄封装） | 三入口 + chatbot.py 自探测 |
| 模型清单/下载 | `tools/fetch_models.sh` | 构建期烘焙 + 运行期补下 + 自检 |
| 模型选择键 | `.env` + `tools/bake.env` | Dockerfile 逐键断言 |
| Qdrant 版本 | Dockerfile ARG | compose 镜像 tag / run_qdrant.sh |
| 发布检查 | `tools/deploy-check.sh` | 五步闸门 |

构建期断言把“烘焙 A、运行 B”变成构建失败；`config-audit.py` 把“废弃键/无消费方键/模型键漂移”变成发布失败；启动日志打印 `.env` sha256 与关键生效值，解决“线上到底跑哪一档”的归因问题。  
**能力边界**：审计用子串匹配，注释命中也会被当成消费方；校验强度低于 AST 级提取。

### 4.6 进程级巡检自愈：用“可运维”替代“容量解决”

2026-10-24 定稿：**不做应用层内存编排**（无互斥驻留、无自适应/水位、无请求级 keep_alive）。每个进程按自身策略管理内存；OOM 的现实后果是某进程被杀，由 entrypoint 的就地重启兜底：

- 存活判据排除僵尸（`kill -0` + `stat != Z`），健康检查用 HTTP；
- 连续失败/退出 → `kill -9` → 指数退避 `min(120s, 5·2^(n-1))·(1+jitter)` 后重启；
- 重启层级：单进程 → 容器内拉起；PID 1/容器退出 → 平台重拉容器（仍属“重启运行”，非重新部署）；
- 配对观测：`[mem]` 打 cgroup anon 与 RSS Top4，`[watchdog]` 每分钟汇总，`_kv_report` 转印 KV 精度。

**评价**：这是对“8G 容量矛盾无法在应用层解决”的诚实工程回应；但它把“容量不足”转化为“周期性短暂不可用”，不是消除。当前 `turns.jsonl` 已有 `insufficient_memory` 实证。

### 4.7 三形态部署与权重三级策略

| 形态 | 入口 | 进程编排 | 检索模型位置 | 适用 |
|---|---|---|---|---|
| 单容器（魔搭） | `Dockerfile` + `entrypoint.sh` | entrypoint 起 qdrant/ollama(/infinity)/streamlit 并巡检 | 进程内 torch（或可选 infinity） | 2vCPU/8G 平台 |
| compose | `docker-compose.yml` | Docker 负责重启 + 健康依赖 | 独立 embed 容器（HTTP） | 自有 Linux / GPU |
| 本地原生 | `tools/run_local.sh` | 脚本起停 + pid/端口/命令行三一致复用 | 可选 infinity 或进程内 | macOS Metal/MPS |

权重三级策略（烘焙镜像 > `/mnt/workspace` 持久盘 > `/app` 就地下载）与 no-bake 配套；运行期用 symlink 而不是重写 `RAG_EMBED_MODEL_PATH`，因为后者会进切分指纹导致本地/线上指纹不一致。  
**能力边界**：no-bake 后若无持久盘，每次重启需重下 ~6 GB；compose 的 app 仍以 `BAKE_*=1` 构建并绕开 entrypoint（见 §7）。

### 4.8 评估方法论：阈值先登记、基线可跨重建

- `quant_parity.py` 在测量前登记阈值（嵌入余弦 ≥0.999、P1 ≥0.995、重排 Spearman ≥0.99、top1 ≥0.95、吞吐 ≥1.2×、常驻下降 ≥50%），防止“测完再改判据”。
- `eval_retrieval.py` 以“来源文档命中”为跨重建不变量（point id 会变，来源不会），并以退出码作为闸门。
- `rerank_parity.py` 在拆分 HTTP 重排前先证明两条路径同一排序。
- `turn_stats.py` 用 `prompt_eval_count / prompt_tokens_est` 判断 KV 复用还是整段重算。

这套方法让“改动是否让系统变坏”可回答；不足是全部离线、手工触发，没有进入 CI，也没有端到端“答得好不好”的 golden QA。

## 6. 架构优势

1. **把“静默失败”当作一等敌人**：从配置解析、日志轮转、GPU 回落到检索降级，几乎每条路径都写明“旧写法会怎样静默错”，并用具名报错/断言/状态位消除。这是本项目最稀缺的工程文化。
2. **产物状态机而非文件堆**：四阶段 + 三类指纹 + fail-closed + 原子别名切换，使“重建”是幂等、可回滚、可诊断的操作。
3. **离线/在线判据同源**：写入与校验共用同一函数（切分指纹、缓存选择、词表指纹），从结构上消除“判据与实现分叉”。
4. **检索链路可解释**：双通道名次、RRF 资源、去重折叠、候选截断、重排分数都进入 steps（API 侧）；权重与候选池策略显式化。
5. **生成预算硬约束**：单一 token 度量 + 整轮淘汰 + 资料整条让位 + RuntimeError 兜底，长上下文下不会静默越界。
6. **失败语义清晰**：error/done 互斥、失败不入历史、Stop 主动断流、空库/清空是合法终态。
7. **配置与构建的单一来源**：dotenv/hw_profile/fetch_models/版本号/模型键各自一处，且用构建断言和审计脚本防漂移。
8. **对平台缺陷的工程化适配**：mtime 归一、gh-proxy、多段下载、infinity 影子视图、OAuth secrets 装配、no-bake、进程自愈——每条都对应真实事故。
9. **评估方法论成熟**：阈值测量前登记、跨重建基线、先对拍再拆分、台账默认关闭——不把“基准测量”变成日常负担。
10. **注释即决策记录**：关键取舍都带日期、实测数字与“为什么不是另一种写法”，降低后续变更的认知成本。

| # | 风险 | 机制与影响 | 证据 |
|---|---|---|---|

### 8.3 H3：平台化（8 周以上，需版本迁移）

1. **多用户**：按登录 ID 持久会话；Qdrant 租户 filter；队列 + 背压 + 并发上限；KV≈f(并发, ctx) 预算公式；限流。
2. **多格式**：PDF/DOCX 解析纳入分块指纹；版面/表格策略。
3. **查询能力**：多轮查询改写（A1）、查询级缓存（C3）、相关性阈值/拒答策略（需产品决策）。
4. **交付与运维**：镜像 digest 固定、备份/快照、发布流程自动化、端到端监控。
5. **容量**：HNSW/量化（当前 int8/int8e/onnx_int8 因保真未达标被拒，但 int8e 内存 −75% 是现成抓手）、检索模型独立服务化。

### 8.4 不建议做的事

- 不要在未解决 P0-2 前继续增强“清空/重建”自动化——会把静默清库放大。
- 不要在单容器 8G 档继续加应用层内存编排——2026-10-24 已论证无效，只会移动 OOM 时机。
- 不要为通过 lint 而改动指纹区源码——触发全量重建且违反不变量；应继续用精确豁免 + 人工核对清单。

## 9. 结论

1. **架构定位准确**：项目选择“单文件 + 单容器 + 强运维”的 appliance 路线，与其部署平台（2vCPU/8G、无 compose）和单用户场景高度匹配；把复杂度集中在“知识正确性”和“运行可恢复”，而不是抽象层次，是正确的取舍。
2. **工程化水平显著高于同规模项目**：指纹/闸门/原子切换、单一来源配置、构建期断言、量化与检索评估方法论，构成了真正可复用的“RAG 生产化经验”。
3. **主要风险不在算法，而在容量与边界治理**：131k × 8G、重复定义导致的静默清库、no-bake 无持久盘、token 预算与真实 prompt 的偏差，是当前最该修的四个点；compose 路径的一致性问题，是“第二条部署路径”的典型债务。
4. **平台化能力尚未建立**：单用户、无租户/限流/持久会话、无测试/CI，决定了它现在是“一套可交付的系统”，而不是“一个可复制的平台”。若目标是多用户 SaaS，应按 README B 档做整组版本迁移，而不是局部打补丁。
5. **建议的下一步**：先做 H1 的 6 个动作（其中 `_document_paths` 与容量档位是最高性价比），再启动 H2 的模块化与 golden QA；在容量与正确性稳定前，不建议扩展多格式或多用户。

## 附录 D：本机部署 vs 远程部署（使用与运维差异）

> “远程”在本文指**魔搭创空间单容器部署**（`Dockerfile` + `entrypoint.sh`，2vCPU/8G，端口 7860）；如无特别说明，“本机”指 **macOS 原生四件套**（`tools/run_local.sh`）。自有 Linux 服务器的 **compose 四容器**作为第三种形态单列。

### D.1 三种形态一句话对照

| 形态 | 启动方式 | 本质差异 |
|---|---|---|
| 本机原生 | `tools/run_local.sh start` | 四个原生进程，直接吃 Metal/MPS，数据与权重都在本机磁盘，无容器层 |
| 远程单容器（魔搭） | `git push` → 平台构建 → entrypoint 起三进程 | 一个镜像 = 一个交付物；CPU-only、8G、可写层不持久、进程级自愈 |
| 自建 compose | `docker compose up -d` | 四个容器隔离、HTTP 检索服务、可 GPU；持久卷、无应用层巡检 |

### D.2 关键差异表

| 维度 | 本机（原生） | 远程（魔搭单容器） | 自建 compose |
|---|---|---|---|
| 编排者 | `run_local.sh`（pid + HTTP 健康） | `entrypoint.sh`（PID 1 监督循环） | Docker + healthcheck |
| 访问入口 | `http://127.0.0.1:8501`（仅回环） | 平台网关 → 容器 `0.0.0.0:7860` | 宿主机 `127.0.0.1:7860` |
| 内部端口 | Qdrant 6333 / Ollama 11434 / infinity 8001 | 同左，但只在容器内 | 服务名互联（qdrant/ollama/embed） |
| 计算设备 | Ollama Metal + torch MPS（可回退 CPU） | 纯 CPU（2vCPU） | 取决于宿主；GPU 覆盖只给 Ollama |
| 生成模型 | `ollama serve` 原生 + Metal | 容器内 `ollama serve` CPU；`RAG_GEN_NUM_GPU=auto` 首次失败回落 | ollama 容器；compose 里 `KEEP_ALIVE=-1` |
| 检索模型后端 | 默认进程内 torch（可用 `run_local.sh models` 起 infinity） | 进程内 torch（镜像故意不装 infinity） | 独立 embed 容器，HTTP 后端 |
| 权重来源 | `./models` + `~/.ollama/models` 已在本地 | 构建期烘焙 **或** no-bake 运行期下载（默认 no-bake，~6 GB） | app 镜像烘焙 + embed 挂载 `./models:ro` |
| 首次启动 | 秒级到分钟级（权重已就位） | 需等权重下载 + 模型加载 + 启动自检；下载窗口内问答失败 | 镜像已带权重；embed 冷加载 120s 起步 |
| 数据/索引来源 | 本地 `artifacts/chunks.json` + `storage/` | 镜像内 `COPY storage/ artifacts/`（来自仓库快照） | app 镜像带数据；`./storage` 挂载持久化 |
| 运行期重建索引 | 常规操作；可用 MPS（约 30 min vs CPU 73 min） | 不推荐：8G 与 serve 同机，`RAG_INDEX_MIN_FREE_MB=2048` 会 fail-closed；且结果只在容器可写层 | 可做，但需停 app 或加大内存；持久化到宿主 |
| 数据持久性 | 全部落盘，重启即恢复 | **可写层不持久**：重启/重部署回滚到镜像快照；仅 `/mnt/workspace` 可写时权重可复用 | 卷持久（storage/models） |
| 配置注入 | `.env` + `run_local.sh` 的 dotenv/hw_profile | 平台环境变量 + `.env` + entrypoint 的 dotenv/hw_profile + 配置指纹日志 | compose `env_file` + 环境变量覆盖 |
| 登录/鉴权 | 无 OAuth → 登录门自动关闭 | 平台可注入 OAUTH_*，entrypoint 生成 secrets；当前 `RAG_LOGIN_ENABLED=0` 关闭 | 默认无鉴权，端口绑回环 |
| 自愈 | 无自动巡检；进程挂了手动 `start` | 进程级巡检 + 指数退避重启；容器退出由平台重拉 | 容器级 `restart`；**无健康检查的 app** 僵死无人管 |
| 观测 | 终端 + `*.log`；无 cgroup 观测 | `[config]/[hw]/[mem]/[watchdog]/[自检]` + 平台日志 | Docker logs + `rag.log`；无 `[mem]` 观测 |
| 冷启动首问 | 快（模型本地、预热可开） | 慢：权重下载、模型加载、指纹闸门首次全量核对 | 中等：镜像本地、embed 冷加载 |
| 可复现性 | 依赖本机环境（Python/ollama/qdrant 二进制） | 镜像 + 依赖锁定，最接近可复现 | 镜像可复现，但多容器编排更复杂 |
| 升级方式 | `git pull` + 重启进程（注意复用可能跑旧代码） | 重新构建/部署镜像；进程内重启不算重部署 | 重建镜像 + `docker compose up -d` |

### D.3 使用上的实际区别

**本机更适合“开发/运维动作”**：`process`、`index`、`sparse`、`stages`、`compare-chunks`、`lexicon` 都可在本机直接跑；可停掉 Ollama 释放 Metal 后再建索引；可直接改代码、改 `.env` 后重启；日志在仓库目录，`tail` 即可。代价是环境不可复制、无自愈、无 cgroup 观测。

**远程更适合“只读问答服务”**：用户只通过平台 URL 进入 Streamlit；重建索引、改配置、升级代码都走“重新构建/部署”流程；容器内可写层的变化（尤其远程跑 `index` 的结果）在重启/重部署后丢失。远程没有 GPU，重排走 CPU（实测 872 ms/候选），因此候选池被压到 `RAG_RERANK_TOP_K=9`；本机 Metal 下同一模型约 41.9 ms/候选，但当前 `.env` 两端共用 9，属于“为远程延迟做的统一折中”。

**命令可用性不同**：远程镜像里 CLI 仍然存在，但平台通常不提供交互 shell；且 8G 档不建议在服务运行时重建。因此“重建索引”事实上是本机动作，远程只消费产物。本机则两种角色都能承担。

### D.4 同一份 `.env` 如何同时适配两端

项目刻意让两端**共用一份配置**，靠以下机制吸收差异：

1. **硬件派生**：线程数、`MALLOC_ARENA_MAX`、Ollama 并行槽位由 `tools/hw_profile.py` 按 cgroup/系统探测；2vCPU 容器算 2，8 核 Mac 算 8，不在 `.env` 写死。
2. **GPU 自动回落**：`RAG_GEN_NUM_GPU=auto` 在本地走 Metal 全 GPU，在纯 CPU 容器首个请求失败后回落 CPU 并记住，不需要第二份配置。
3. **权重路径 symlink**：远程三级权重策略把权重放到 `/mnt/workspace` 或 `/app/models`，但**不重写** `RAG_EMBED_MODEL_PATH` 字面量，而是用 symlink 落位——否则相对路径变化会进切分指纹，导致本地/远程指纹不同源、检索闸门 fail-closed。
4. **后端开关**：单容器用进程内 torch，compose 用 `RAG_*_BACKEND=http`，同一份代码、同一份模型。
5. **内存闸门**：`RAG_INDEX_MIN_FREE_MB` 只在能读到 MemAvailable 的环境生效；macOS 读不到时显式跳过并说明，不会假装“检查过了”。

### D.5 数据更新的标准流程（远程部署尤其重要）

1. 本机改语料/词表/切分参数 → `python chatbot.py process`（必要时 `index` / `sparse`）；
2. 本机跑 `python chatbot.py stages` 确认四段全绿；
3. **同时更新** `artifacts/chunks.json`、`artifacts/chunks.meta.json` 与 `storage/` 快照——远程镜像靠这两者同源；
4. 提交（`storage/` 虽在 .gitignore 中，但已被历史 `-f` 入仓；新增集合文件需要显式 `git add -f`）；
5. 重新构建/部署远程镜像。

只更新 `chunks.json` 不更新 `storage/`（或相反）会让远程出现“分块指纹与集合 payload 不一致”，在线闸门会拒绝检索——这是有意的 fail-closed，不是远程 bug。

### D.6 常见坑

1. **本地重建后只 push 一半产物** → 远程指纹/点数不一致，检索报错（见 D.5）。
2. **在远程跑 `index` 后重启** → 重建结果在容器可写层，重启/重部署丢失，看起来像“重建没生效”。
3. **本地 `run_local.sh start` 复用旧进程** → 改代码/改 `.env` 后未 `stop`，跑的是旧进程；远程重新部署则不会。
4. **远程首次启动就提问** → 权重仍在后台下载，首问可能失败；等启动自检/下载完成或预热后再用。
5. **两端都开 `RAG_TURN_STATS=1` 写同一路径** → 多进程追加交错；该开关是诊断用，稳定后应关闭。
6. **在远程依赖 GPU 档** → 纯 CPU 容器没有 Metal/CUDA，`auto` 会回落；重排/索引延迟按 CPU 预期，不要按本机数字评估。

### D.7 选择建议

| 目标 | 推荐形态 |
|---|---|
| 开发调试、重建索引、评估对拍、改语料 | 本机原生 |
| 对外演示、长期在线、低人工运维、单用户 | 远程单容器（魔搭） |
| 自有服务器、需要 GPU、要多容器隔离/持久卷 | compose（NVIDIA 主机叠加 gpu 覆盖） |
| 多用户/多租户/高并发 | 以上都不够，需先做 README B 档迁移 |

## 附录 E：CPU/GPU 统一路径与“质效最大化”评估（2026-10-25）

### E.1 先回答三个问题

| 问题 | 结论 |
|---|---|
| 当前代码兼容 CPU/GPU 吗？ | **兼容**。PyTorch 路径不依赖 CUDA 专有算子，生成侧由 Ollama 抽象设备；本机 MPS、容器 CPU 都已跑通。 |
| 当前方案是“最大质效”吗？ | **不是**。当前是“质量优先（131k 上下文）+ 延迟折中（重排 9 条）”的混合档，不是按部署形态测出来的 Pareto 最优点；且缺少 golden QA，“质”无法被证明。 |
| 能做成“代码零分支”吗？ | **字面零分支不可能**（设备发现、dtype 支持、失败回落必须有判定）；但可以做到“**业务代码零设备分支**”：只在构造 `RuntimeProfile` 时判定一次，下游全部读字段。 |

### E.2 现有分支盘点（可消除 vs 不可消除）

| 位置（当前工作副本） | 分支 | 性质 | 处置 |
|---|---|---|---|
| `get_device()`（1081） | MPS → CUDA → CPU | 设备发现 | 收敛到 `torch.accelerator.current_accelerator()`，仍是一处 |
| `_float16_ok()`（1090） | mps/cuda 用 fp16，CPU fp32 | 精度策略 | 变成 `profile.dtype`，不再在调用点判断 |
| `embed_batch_size()`（284） | 按设备/内存给不同批大小 | 性能调参 | 保留在 profile 构造；运行期用自适应批（OOM 减半） |
| `_RERANK_MS_PER_CAND`（791） | 按设备名查硬编码延迟 | 观测/选池 | 改为实测或配置，删掉设备名分支 |
| 索引 `use_gpu` + `model.half()` + 失败回退（2495） | GPU 文件单独路径 | 性能 + 健壮性 | 统一 `model.to(profile.device, dtype=profile.dtype)`；加载失败回退归 profile 构造 |
| `_mps_empty_cache()`（1312、2542、2578） | 仅 MPS 清缓存 | 内存管理 | 变成 profile 的 `empty_cache()` 回调（可为空函数） |
| `stream_chat` GPU 回落（688） | 非 200 去 num_gpu 重发 | 跨设备兼容 | 应用不再发 `num_gpu`，交给部署侧 Ollama 配置；删掉回落分支 |
| `EMBED_BACKEND == "http"`（3803、3818、3877） | torch/http 两条检索路径 | 部署形态 | 抽 `EmbeddingBackend.embed_query()` / `Reranker.rerank()` 接口，调用点一条路径 |
| 最新提交的 HTTP 并发分支（稀疏与嵌入并行） | 仅 HTTP 后端走特殊并发 | 性能优化 | 泛化为“先提交稀疏 future，再算稠密向量，再查稠密”，两种后端同一时序 |

结论：真正**必须保留**的只有“profile 构造 + 失败回退包装”两处；其余都可以变成数据（字段/接口），而不是散落的 `if device == ...`。

### E.3 目标结构（伪代码）

~~~python
# runtime_profile.py —— 全仓唯一设备判定点
@dataclass(frozen=True)
class RuntimeProfile:
    device: torch.device
    dtype: torch.dtype          # fp16 on GPU, fp32 on CPU（或 bf16，经评测决定）
    amp: bool
    batch: int                  # 初始值；运行期自适应
    threads: int
    empty_cache: Callable[[], None]

def build_runtime_profile() -> RuntimeProfile:
    acc = torch.accelerator.current_accelerator()   # 无加速器返回 None
    if acc is None:
        return RuntimeProfile(torch.device("cpu"), torch.float32, False, 32, hw_cores(), lambda: None)
    # GPU/MPS 分支只出现在这里
    ...

# 业务代码：只有一条路径
model = AutoModel.from_pretrained(path, torch_dtype=PROFILE.dtype).to(PROFILE.device)
with torch.inference_mode(), torch.autocast(device_type=PROFILE.device.type,
                                             dtype=PROFILE.dtype,
                                             enabled=PROFILE.amp):
    out = model(**inputs)
~~~

生成侧：应用不发送 `num_gpu`；本机/远程各自在**拉起 Ollama 的环境**里配置（两套部署配置，而不是两套代码路径）。检索侧：`EmbeddingBackend` / `Reranker` 两个接口，torch 与 HTTP 是两种实现，`hybrid_search` 只有一条编排路径。

### E.4 “最大质效”的评估与压榨顺序

1. **先补“质”的度量**（当前缺 golden QA）：30–50 条问题 + 期望来源 + 关键点；用 `eval_retrieval` 的 source_hit/top1 只能测召回，不能测答案。
2. **建立 profile 矩阵**：`ctx ∈ {32k, 64k, 131k}` × `rerank ∈ {9, 20}` × `think ∈ {0,1}` × `dtype ∈ {fp32, fp16}` × `batch ∈ {16, 32}`；每种组合跑：答案质量、source_hit、检索/生成耗时 p50/p95、峰值内存、OOM 次数。
3. **按部署定档**：本机 GPU 档（131k / rerank 20 / fp16 / think 1）与远程 CPU 档（32k / rerank 9 / fp32 / think 1）各一套 `.env` profile；代码完全一致。
4. **优化顺序**（按当前实测瓶颈）：
   - CPU 重排是最大延迟项（872 ms/候选 × 9 ≈ 7.8 s）：先评测更小重排模型 / ONNX / 线程调优，再决定是否降候选。
   - 生成 prefill 是第二项：远程降 ctx 或限制输出；用 `turn_stats` 的 `prompt_eval_count/prompt_tokens_est` 验证 KV 复用。
   - 检索：多轮查询改写（A1）对“质”的提升可能大于调 top_k；查询缓存对“效”有边际收益。
   - 嵌入/批处理：自适应批 + 线程数已经是硬件派生；收益有限，不建议先动。
5. **不要做的事**：为“零分支”强行让 CPU 也用 fp16（更慢且可能改变数值）；为“最大质效”同时保留 131k + 20 候选 + 无限输出（8G 必 OOM）。

### E.5 验收标准

- 全仓 grep：除 `runtime_profile.py` 与后端工厂外，不再出现 `device == "mps"/"cuda"`、`.half()`、`_mps_empty_cache`、`num_gpu` 等设备判断。
- 同一份单测/评测在 CPU 与 GPU 上跑同一套用例；质量差异用 `rerank_parity` 与 golden QA 量化。
- 两套 profile 的 stages/检索结果在相同产物下一致（质量口径），延迟/内存各自达标。
- 新增分支必须能回答：“这是设备差异，还是业务策略？”——设备差异只能进 profile，业务策略只能进配置。

> 结论：**兼容性已经具备，零设备分支可以通过“一次探测 + 数据化 profile + 接口化后端”做到；当前不是质效最大，需要先用 golden QA 与 profile 矩阵把“最大”定义出来，再按部署形态固化成两套配置，而不是继续在代码里加设备分支。**

## 附录 F：函数式 + 表驱动 + AOP 的重构设计（高内聚、低耦合）

> 目标不是“把代码改成函数式”或“到处用字典”，而是**给每类关注点选最合适的范式**：纯逻辑用函数式，状态与资源用对象，流程编排用过程式，横切能力用 AOP（装饰器/上下文管理器）。原则：**能用数据/表表达的分支，不要写成 if/elif 链；能用纯函数表达的变换，不要碰 I/O 和全局状态。**

### F.1 三种范式的分工（不要互相越界）

| 代码类型 | 最适合 | 判据 | 例子 |
|---|---|---|---|
| 纯变换：文本→分块、命中→排序、消息→prompt | 函数式 | 同样输入必得同样输出，无 I/O | normalize/ chunk / weighted_rrf / plan_generation |
| 有状态资源：模型、Qdrant 客户端、HTTP 会话、引擎 | 面向对象 | 有生命周期、连接池、懒加载、锁 | RAGEngine、TorchEmbedder、OllamaChatClient |
| 入口与编排：CLI、启动、一次问答时序 | 过程式 | 顺序步骤 + 失败出口 | run_turn、cmd_index、run_streamlit |
| 横切：日志、计时、重试、锁、降级记录、校验 | 切面式 | 与业务无关、可组合 | @timed、@with_retry、@locked、@record_degradation |
| 分支映射：≥3 个且会增长的变体 | 表驱动/字典 | 变体=数据，不是控制流 | COMMANDS、STAGES、BACKENDS、FIELD_SPECS |

**判断规则**：分支只有 2 个且稳定（如“有/无”），普通 if 更可读；分支 ≥3 个、且未来会新增（命令、阶段、后端、字段、错误类型），才升级为映射表。不要为了“无分支”把简单判断也塞进字典。

### F.2 现有代码里已经值得保留的表驱动资产

- @@COMMANDS@@：命令集的单点真相，同时驱动 usage 与 argparse（已有）。
- @@_PAYLOAD_SPEC@@ / @@_RECORD_FIELDS@@：记录↔payload 的字段映射（已有）。
- @@EVENT_*@@ 封闭词表 + @@drain_events@@ 的 @@acc/sink@@ 字典（已有，天然可扩展为 handler 注册表）。
- @@_ENV_TRUE/_ENV_FALSE@@ 白名单、@@_CHUNKING_CODE_UNITS@@ 指纹单元清单（已有）。
- @@RAGEngine@@ 支持注入 @@client/embed/rerank@@、@@run_turn@@ 支持注入 @@chat@@（已有的依赖倒置雏形）。

重构应**扩大**这些模式，而不是推倒重来。

### F.4 五类典型分支的替换方法

**1）配置字段 → 字段注册表（数据驱动）**

~~~python
@dataclass(frozen=True)
class Field:
    name: str; default: object; parser: Callable[[str], object] = str
    minimum: int | None = None; choices: frozenset[str] | None = None

FIELDS = (
    Field("RAG_TOP_K", 5, int, minimum=1),
    Field("RAG_EMBED_BACKEND", "torch", str, choices=frozenset({"torch", "http"})),
    ...
)  # 新增配置只加一行数据，不加 if

def load_config(env: Mapping[str, str]) -> Config:
    raw = {f.name: _read(env, f) for f in FIELDS}   # _read 统一空值/报错
    return Config(**raw)
~~~

价值：配置校验从“散落在 1000 行 import 期”变成“一张表 + 一个纯函数”，可单测、可审计；这也是现有 @@config-audit.py@@ 的天然搭档。

**2）命令/阶段 → 注册表（已有 COMMANDS，推广到 stages）**

~~~python
STAGE_CHECKS: dict[str, Callable[[StageContext], StageResult]] = {
    "A": check_chunks, "B": check_embed_cache,
    "C": check_sparse, "D": check_collection,
}

def run_stages(ctx: StageContext) -> StageReport:

    stale = [c for c, r in results.items() if r.stale]
~~~

价值：不再有 @@if "A" in stale / elif "B" ...@@ 的链；新增阶段只注册，不改 @@run_stages@@。

**3）后端/设备 → Protocol + 工厂（对应附录 E）**

~~~python
class Embedder(Protocol):
    def embed(self, texts: Sequence[str], *, is_query: bool) -> list[list[float]]: ...

EMBEDDER_FACTORIES: dict[str, Callable[[Config], Embedder]] = {
    "torch": TorchEmbedder.from_config,
    "http": HttpEmbedder.from_config,

def make_embedder(cfg: Config) -> Embedder:
~~~

价值：@@hybrid_search@@ 只有一条路径；torch/http 的差异在适配器内部，不再出现 @@if EMBED_BACKEND == "http"@@。

**4）降级/错误 → 错误类型 + 映射（而不是到处 try/except 判断）**

~~~python
class RagError(Exception): ...
class GateError(RagError): ...
class RetryableError(RagError): ...

DEGRADE_MESSAGES = {
~~~

价值：降级从“随手打日志”变成“有类型、有码、可统计”的事件；未来可以在 UI/API 统一消费。

### F.5 AOP：用装饰器/上下文管理器收拢横切关注点

~~~python
def timed(label: str, sink: Callable[[str, float], None] = log_timing):
    def wrap(fn):
        @functools.wraps(fn)
        def inner(*a, **kw):
            t0 = time.perf_counter()
            try:
                return fn(*a, **kw)
            finally:
                sink(label, time.perf_counter() - t0)
        return inner
    return wrap

def with_retry(attempts=2, retryable=(ConnectionError, TimeoutError)):
    ...  # 只重试 RetryableError；不吞业务异常

@contextmanager
def inference_lock(lock: threading.Lock):
    with lock:
        yield
~~~

**红线**：不要把装饰器加到 @@_CHUNKING_CODE_UNITS@@ / @@_embed_code_fingerprint@@ / @@lexicon_fingerprint@@ 里的函数上——@@inspect.getsource@@ 会包含装饰器行，指纹变化 = 全量重建。横切能力要么加在调用点，要么加在非指纹函数上。

### F.6 Pythonic 命名建议（仅限非指纹区）

| 现状 | 建议 | 说明 |
|---|---|---|
| @@_state_ref()@@ | @@runtime_state()@@ | 返回进程级单例，名字表达意图 |
| @@_chunk_value()@@ | @@field_or_default()@@ | 通用取值，不做“chunk 专属” |
| @@_get_gen_tokenizer()@@ | @@gen_tokenizer()@@ | 去掉 get_ 前缀，Python 常用法 |
| @@_load_doc_chunks@@ | @@load_document_chunks@@ | 名词完整，避免 doc 歧义 |
| @@_check_chunk_freshness@@ | @@ensure_chunks_fresh@@ | 动词表达“保证”而非“检查” |
| @@RAGEngine.hybrid_search@@ | 保留（领域词） | hybrid 是检索术语，不必改 |
| @@cmd_*@@ | @@command_*@@ 或保留 | CLI 入口保持 __cmd 前缀可读性即可 |
| @@_Embedder@@ 类 | @@TorchEmbedder / HttpEmbedder@@ | 一个类一件事，名字即实现 |

**注意**：@@read_book_text@@、@@parse_aliases@@、@@_hierarchical_split@@、@@_balanced_pack_groups@@ 等名字在指纹单元清单里，**改名 = 指纹漂移 = 全量重建**。命名美化要么跳过它们，要么接受一次重建并同步产物。

### F.7 依赖注入与组合根（低耦合的关键）

~~~python
# engine.py：只依赖抽象，不 import 全局配置
class RagEngine:
    def __init__(self, store: ChunkStore, embedder: Embedder,
                 reranker: Reranker, cfg: Config):
        ...

# composition root：唯一知道“用什么实现”的地方
def build_engine(cfg: Config, profile: RuntimeProfile) -> RagEngine:
    store = QdrantChunkStore(cfg.qdrant, timeout=cfg.qdrant_timeout)
    embedder = make_embedder(cfg, profile)
    reranker = make_reranker(cfg, profile)
    return RagEngine(store, embedder, reranker, cfg)
~~~

好处：@@hybrid_search@@ 可用内存假实现单测；换后端/换设备不改引擎；全局 @@os.getenv@@ 不再散落在业务函数里。

### F.8 迁移顺序（行为等价，指纹不变）

| 步骤 | 动作 | 验收 |
|---|---|---|
| 0 | 冻结指纹：记录 @@chunks.meta.json@@ 的 fingerprint、跑 @@stages@@ 全绿；存 @@compare-chunks@@ 基线 | 基线可复现 |
| 1 | 把纯函数**原样搬**到新模块（源码逐字不变、函数名不变） | 指纹不变；@@process@@ 产物逐字节一致 |
| 2 | 引入 @@Config@@ dataclass 与 @@load_config(env)@@，替换全局常量读取 | 启动日志配置值与旧版一致；非法值仍报错 |
| 3 | 抽 @@Embedder/Reranker/ChatClient/ChunkStore@@ 接口与适配器 | 同一请求在 torch/http 下结果一致（rerank_parity） |
| 4 | @@RAGEngine@@ 改为构造注入；删全局单例直读 | 单测用假对象通过；运行时行为不变 |
| 5 | 分支表驱动化：STAGES/BACKENDS/DEGRADE/HANDLERS | 分支数下降；@@stages@@/CLI 输出不变 |
| 6 | 加 AOP：计时/重试/锁/降级记录（避开指纹函数） | 日志字段增加但业务输出不变 |
| 7 | 拆 @@@chatbot.py@@ 壳，保留旧入口 @@from app.cli import main@@ | @@python chatbot.py ...@@ 完全兼容 |
| 8 | 加单测 + CI（纯函数、表注册、配置校验、指纹快照） | 覆盖率目标：domain ≥70%，适配器用 fake |

**每步都可独立发布**；任一步失败可回滚到上一步，不影响线上。

### F.9 最后的设计判据

1. **高内聚**：一个模块只有一个变化原因（分块、融合、装配、传输各自独立）；纯函数不 import 适配器。
2. **低耦合**：引擎只依赖 Protocol；配置由组合根注入；适配器之间不互相 import；方向永远是 @@app → domain / adapters → domain@@，domain 不反向依赖。
3. **可测试**：核心逻辑（分块、融合、预算、指纹）不碰网络/磁盘；适配器用 fake 实现。
4. **可演进**：新增阶段/命令/后端/降级码 = 加一行注册，不改调度器；新增设备 = 改 profile 构造，不改业务。
5. **不教条**：2 个稳定分支保留 if；只有会增长的分支才表驱动。AOP 只包裹横切，不包裹领域逻辑。

> 一句话：**函数式负责“数据怎么变”，OOP 负责“资源和生命周期”，过程式负责“先做什么后做什么”，AOP 负责“日志/计时/重试/锁”，表驱动负责“有几种、会增长的选择”。这样拆完，单文件变成组合根 + 纯核心 + 适配器三层，高内聚低耦合才是可验收的，而不是口号。**

## 附录 G：单文件内的“函数式核心 + 表驱动 + OOP + 过程式壳”

> 约束：**不拆模块，全部在一个 Streamlit 脚本里完成；前端是唯一入口，业务处理流程也在同一文件。**
> 结论先说：**单文件完全可以做到高内聚、低耦合**。模块化只是物理隔离手段，不是必要条件；单文件靠“逻辑分层 + 依赖方向 + 命名/区域约定 + 自动化检查”替代 import 边界。真正决定耦合的是**依赖方向**，不是文件个数。

### G.1 函数式 vs 过程式：不是风格之争，是“副作用放哪”的分工

| 维度 | 过程式（Procedural） | 函数式（Functional） |
|---|---|---|
| 基本单位 | 步骤/子程序 | 纯函数/表达式 |
| 关注点 | 先做什么、后做什么（how） | 输入到输出是什么（what） |
| 状态 | 就地修改变量/对象 | 参数进、返回值出，不修改外部状态 |
| 控制流 | if/for/while 显式编排 | 组合/comprehension/HOF/生成器 |
| 副作用 | 允许，且常与逻辑混合 | 尽量隔离到边界（I/O 外壳） |
| 测试 | 需要 mock 环境 | 直接给输入断言输出 |
| 适合 | 启动、CLI、一次问答时序、资源生命周期 | 归一化、分块、融合、预算、上下文装配、指纹 |

**同一个去重逻辑的两种写法**：

~~~python
# 过程式：就地维护 seen/kept，直观
def dedup_by_parent(cands):
    kept, seen = [], set()
    for c in cands:
        key = c.get("parent_id") or c.get("id")
        if key not in seen:
            seen.add(key); kept.append(c)
    return kept

# 函数式（Pythonic）：用 dict 保序 + setdefault 表达“每个 key 只留第一个”
def dedup_by_parent(cands):
    best = {}
    for c in cands:
        best.setdefault(c.get("parent_id") or c.get("id"), c)
    return list(best.values())
~~~

两者都没有错。**过程式负责“顺序与副作用”，函数式负责“数据变换”**；把两者混在一起才是问题：在纯变换里读全局变量、打日志、碰网络，就会既难测又难复用。

**Python 的函数式不是 Haskell**：不追求 point-free、不滥用 @@map/lambda@@、不用 @@reduce@@ 硬套循环。Pythonic 的函数式 = 纯函数 + 生成器 + dataclass(frozen) + 一等函数 + 字典/注册表 + @@functools@@（lru_cache/partial/wraps）。

### G.2 能不能“都用函数式 + 字典 + OOP”？

可以，但“都用”要理解成**分工**，不是把所有代码写成一种风格：

| 组成 | 负责 | 不能做什么 |
|---|---|---|
| 函数式核心 | 纯数据变换 | 不能处理 Streamlit 会话、网络、模型生命周期（这些本质有副作用） |
| 字典/注册表 | 有 3+ 变体且会增长的选择 | 不能替代 2 路稳定判断（会降低可读性） |
| OOP | 有状态资源、连接池、懒加载、锁 | 不能变成“什么都往里塞”的上帝对象 |
| 过程式壳 | 入口、一次问答时序、启动/关闭 | 不能把业务规则写进 UI 流程 |
| AOP | 日志/计时/重试/锁/降级记录 | 不能包裹指纹函数（会改指纹） |

一句话：**纯函数式做不了 Streamlit 应用**（UI 状态、流式网络、模型加载都是副作用）；**纯过程式会回到现在的 5,000 行面条**；**纯 OOP 会造出上帝对象**。正确形态是 **Functional Core, Imperative Shell**（函数式核心 + 命令式外壳），字典做策略表，OOP 做资源边界，AOP 做横切。

### G.3 单文件分层蓝图（从上到下，依赖只能向下）

~~~text
§0  imports / typing / 常量与指纹区（禁改区）
§1  值对象与协议：Config、RuntimeProfile、ChunkStore、Embedder、Reranker、ChatClient、Event
§2  纯函数层（domain）：normalize / chunk / token / rrf / dedup / context / prompt / fingerprint
§3  适配器层（有状态）：QdrantChunkStore / TorchEmbedder / HttpEmbedder / TorchReranker /
      HttpReranker / OllamaChatClient / ArtifactStore
§4  引擎层（OOP）：RagEngine（只依赖 §1 协议 + §2 纯函数）
§5  编排层（过程式/生成器）：run_turn / process_all / index_all / sparse_all / stages_report
§6  交互层（Streamlit）：页面、session_state、登录门、Stop、流式渲染
§7  组合根与入口：build_engine() / main() / Streamlit 上下文检测
~~~

依赖方向：**§6 → §5 → §4 → §3 → §2**；§2 不 import §3/§4/§6；§4 不 import §6/Streamlit；§6 只做 UI，不写业务规则。单文件也能用“区域 + 命名 + 检查”强制这个方向。

### G.4 单文件里怎么保证高内聚低耦合

**1）用“区域”替代模块边界**：每段以固定横幅开头（@@# ── L2 domain/pure ──@@），并在文件头写“依赖方向图”。review 时先看跨区调用是否越界。

**2）用协议 + 构造注入替代全局单例直读**：

~~~python
class ChunkStore(Protocol):
    def fetch(self, ids: Sequence[int], collection: str) -> dict[int, dict]: ...
    def search_dense(self, vec, limit, flt): ...
    def search_sparse(self, doc, limit, flt): ...

class RagEngine:
    def __init__(self, store: ChunkStore, embedder: Embedder,
                 reranker: Reranker, cfg: Config, profile: RuntimeProfile):
        ...
~~~

业务层不再出现 @@QDRANT_HOST@@、@@os.getenv@@、@@st.session_state@@；测试时传 fake。

**3）用 grep 做“架构测试”**（单文件没有 import 边界，就用行号/区域约束）：

~~~bash
# st.* 只允许出现在 §6 之后
awk '/── L6 ui/{in_ui=1} in_ui && /st\./{print NR": "$0}' chatbot.py
# os.getenv 只允许出现在 §1 配置区
awk '/── L1 config/{in_cfg=1} /── L2 domain/{in_cfg=0} in_cfg && /os\.getenv/{print NR": "$0}' chatbot.py
# requests/qdrant_client/torch 只允许出现在 §3/§4
~~~

这不是形式主义：它把“单文件必然耦合”的默认趋势按住。

**4）纯函数一律显式传参**：不读全局常量、不写日志、不碰 @@st@@。需要的配置作为参数传入（@@cfg@@ / @@profile@@）。这样纯函数可以单测、可以缓存、可以并行。

**5）OOP 只包“有生命周期的东西”**：连接、模型、锁、HTTP 会话、缓存目录；值对象用 @@@dataclass(frozen=True)@@。不要为“每类数据”建一个类。

**6）表驱动只收“会增长的变体”**：命令、阶段、后端、字段、降级码、事件 handler、上下文格式；两路稳定判断保留 if。

### G.5 Streamlit 单脚本的特别约束（很重要）

Streamlit 每次交互都**从头重跑整个脚本**，所以单文件架构必须遵守：

1. **顶层只放“便宜且幂等”的东西**：常量、类型、纯函数定义；配置解析要轻量，重活放到缓存资源里。
2. **重资源用 @@st.cache_resource@@**：@@build_engine()@@、@@RuntimeProfile@@、@@Config@@、模型/客户端单例；保证整个进程一份，而不是每次 rerun 重建。
3. **@@st.session_state@@ 只在 §6 出现**：messages、count 缓存、登录态；业务函数只接收 @@history@@ 参数，不知道 session 的存在。
4. **流式用生成器 + 事件**：@@run_turn()@@ 产出 @@retrieval/thinking/delta/error/done@@，UI 消费；这样将来加 API 入口不用改业务。
5. **懒加载第三方库**：torch/transformers/qdrant_client 在函数内 import；避免每次 rerun 都付 import 成本（当前代码已这样做）。
6. **入口二选一**：@@get_script_run_ctx()@@ 判断是否在 Streamlit；否则走 @@main(argv)@@。单文件同时支持“前端入口”和“运维 CLI”。
7. **长任务不要阻塞 UI**：@@process/index@@ 不建议在 Streamlit 会话里跑（会卡住 rerun）；保留 CLI 路径，UI 只做问答。

### G.6 单文件里的表驱动清单（建议改 / 不建议改）

| 适合表驱动 | 当前/建议 |
|---|---|
| 命令分发 | @@COMMANDS@@（已有，保留） |
| 字段映射 | @@_PAYLOAD_SPEC@@（已有，保留） |
| 事件词表 | @@EVENT_*@@ + handler 表（扩展） |
| 阶段检查 | @@STAGE_CHECKS = {"A": ..., "B": ...}@@（替换 if/elif） |
| 后端工厂 | @@EMBEDDER_FACTORIES/RERANKER_FACTORIES@@ |
| 配置字段 | @@FIELDS = (Field(...), ...)@@ + 一个 @@load_config(env)@@ |
| 降级码 | @@DEGRADE_MESSAGES@@ + @@Degradation@@ 值对象 |
| 上下文格式 | @@CONTEXT_FORMATTERS@@（meta/labels/tags/plain） |
| 错误提示 | @@ERROR_HINTS@@（404/OOM/超时/连接） |

| 类 | 职责 | 状态 |
|---|---|---|
| @@Config@@ | 只读配置值对象 | dataclass(frozen) |
| @@RuntimeProfile@@ | 设备/精度/批大小/线程 | dataclass(frozen) + 一次探测 |
| @@ArtifactStore@@ | chunks/meta/缓存文件读写 | 路径 + 原子写 |

### G.8 AOP 清单（单文件内可落地）

| 切面 | 实现 | 注意 |
|---|---|---|
| 计时 | @@@timed("retrieval")@@ 装饰器 | 只记录，不改返回值 |
| 重试 | @@with_retry(attempts, retryable)@@ | 只重试明确的 RetryableError |
| 锁 | @@@contextmanager def inference_lock()@@ | 不嵌套同一把锁 |
| 降级记录 | @@record_degradation(code)@@ | 结构化，不打断主流程 |
| 配置校验 | @@validate(cfg)@@ 在组合根一次性执行 | 不在业务函数里零散 raise |

**红线**：指纹单元（@@_CHUNKING_CODE_UNITS@@、@@_embed_code_fingerprint@@、@@lexicon_fingerprint@@ 列出的函数）不能加装饰器/改名——@@inspect.getsource@@ 变化会让指纹漂移，触发全量重建。

### G.9 单文件 vs 多文件：取舍

| 维度 | 单文件（你的约束） | 多模块 |
|---|---|---|
| 部署/复制 | **最简单**：一个文件 + 数据/模型 | 需要包结构、import 路径 |
| 边界强制 | 靠约定 + grep 检查 | import 自然隔离 |
| 可测试性 | 需要 @@if __name__@@ / 惰性配置辅助 | 直接 import 子模块 |
| 阅读成本 | 依赖清晰的区域与命名 | 文件树即导航 |
| 耦合风险 | 高（容易随手跨层调用） | 低（跨层需显式 import） |
| 适合阶段 | 单租户、单人维护、快速交付 | 多团队、长期演进、多入口 |

结论：**当前约束下单文件是合理选择**；但要把“单文件”当成分层架构来写，而不是当垃圾桶。

### G.10 单文件内的迁移顺序（行为等价）

1. 文件头写“区域地图 + 依赖方向”，把现有函数按 §2/§3/§4/§5/§6 归位（只移动、不改源码）；
2. 纯函数去副作用：显式传 @@cfg@@/@@profile@@，不在里面读全局；指纹函数除外；
3. 抽 @@Config@@/@@RuntimeProfile@@ 值对象，组合根一次性构造；
4. 抽 4 个 Protocol + 适配器类，@@RagEngine@@ 构造注入；
5. 把 if/elif 链替换为注册表（先 stages/commands/backends，后其它）；
6. 加 AOP 装饰器（避开指纹区）；
7. 用 grep 架构检查 + 纯函数单测锁住分层；
8. 最后再考虑物理拆模块（如果将来需要）。

> 一句话：**函数式负责“数据怎么变”，过程式负责“流程怎么走”，OOP 负责“资源怎么活”，字典负责“选择有几种”，AOP 负责“横切怎么收”。单文件里也可以有清晰的三层依赖；高内聚低耦合是“依赖方向 + 数据流”的结果，不是文件数量。**
